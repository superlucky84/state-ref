# CI-22 — 경로 트리 수명에 대한 보충 측정

`DC-13`은 **(a) 문서화 + 경계 테스트로 해소됐다**(`DESIGN.md` §4, 커밋 `cd3bbb3`). 이 문서는 그 결정을 재검토하지 않는다.

여기 있는 것은 **측정값과 그 조건뿐이다.** `DC-13`의 ④(진짜 수정의 모양)나 ⑤(부분 완화안)를 나중에 다시 꺼낼 때, 근거를 처음부터 다시 만들지 않으려고 남긴다. 권고도 설계안도 담지 않는다.

- 기준: `c159041` / Node 20.3.0 / 측정 2026-09-17
- 관련: `REQUIREMENTS.md` §3.6(문제 재현) · `DESIGN.md` §3.4·`DC-13`(구조와 결정) · `src/tests/core/tree-lifetime.ts`(고정된 불변식)

## 1. 측정의 성격

이 문서의 숫자는 성격이 셋으로 갈린다. 섞어 읽으면 안 된다.

| 구간 | 성격 |
|---|---|
| §2, §3-1, §4 | **실제 코어 측정.** `dist/state-ref.mjs` 사용 |
| §3-2 | **모델.** `makeNode`와 같은 모양의 평범한 객체 |
| §5 | **모델 프로토타입.** 코어에 넣은 수치가 아니다 |

노드 수를 직접 센 측정은 `create()` 반환에 `__pathRoot: pathRoot`를 임시로 추가하고 `createStore`에서 `watch`에 얹은 뒤, in-source 테스트(`vite.config.js`의 `includeSource`)에서 재귀로 셌다. **측정 후 되돌렸다. 소스에는 남아 있지 않다.**

## 2. 수명 — 무엇이 언제 회수되는가

### 2-1. GC는 정상 동작한다

`PathNode`가 GC에서 제외된 객체라는 오해를 없애기 위한 측정. 10,000 경로 접근(**구독 없이 쓰기만**) 후 뿌리를 단계적으로 끊는다:

| 단계 | heap | 회수된 것 |
|---|---|---|
| 접근 직후 | +16.4 MB | — |
| `ref = null` + GC | +5.0 MB | 프록시·렌즈 트리 (경로당 **1222 B**) |
| `watch = null` + GC | **+0.4 MB** | PathNode 트리 (경로당 **495 B**) |

**스토어를 놓으면 노드도 전부 회수된다.** 고전적 누수가 아니라 수명 불일치다.

부수적으로, 회수되는 쪽(프록시 1222 B)이 남는 쪽(노드 495 B)보다 **2.5배 비싸다.** 비용의 다수는 원래 회수되는 구조에 있고, 남는 것은 싼 쪽이다.

### 2-2. 프록시 회수의 조건은 "`ref`를 놓는 것"이 아니다

§2-1은 **구독이 없는** 경우다. 구독이 있으면 다르다. 같은 10,000 경로, 구독 1개를 건 채로:

| 단계 | heap | `items[7]` 프록시 |
|---|---|---|
| 접근 직후 | +16.4 MB | 생존 |
| `ref = null` (**구독은 살아있음**) | +16.5 MB | **생존** |
| `ctrl.abort()` + `ctrl = null` | **+5.0 MB** | 회수됨 |

`storeRenderList`가 강참조 `Map<Run, ...>`이고 `run` 클로저가 `ref`를, `ref`가 루트 프록시를 붙든다. 따라서 **프록시 트리는 `ref`를 놓아도 구독이 살아있으면 남는다.**

> **함정 — 측정 중 실제로 걸렸다.** `abort` 리스너(`connectors/runner.ts:140`)는 `renew`와 `run`을 클로저로 잡고 `signal`에 붙은 채 제거되지 않는다. 그래서 `AbortController`를 계속 들고 있으면 **abort 이후에도** 프록시 트리가 회수되지 않는다. 위 표의 3행에서 `ctrl = null`이 필요했던 이유다. 커넥터는 컨트롤러를 컴포넌트 스코프에 두므로 언마운트 시 함께 사라지지만, 컨트롤러를 모듈 스코프에 두는 코드에서는 해당하지 않는다.

정리하면 회수 조건은 이렇다:

| 대상 | 회수되는 조건 |
|---|---|
| 프록시·렌즈 트리 | 구독 해제 **그리고** `ref`·`AbortController` 참조를 모두 놓을 것 |
| PathNode 트리 | **스토어(`watch`) 자체를 놓을 것** |

`DC-13` ①이 말한 `childProxies` 누적은 **`ref`가 살아있는 동안**의 이야기이고, 위 측정과 모순되지 않는다. `childProxies`는 프록시 클로저 안에 있어 뿌리가 죽으면 통째로 따라 죽는다.

## 3. 노드 하나의 비용

### 3-1. 실제 코어: 경로당 495 B

§2-1의 3단계 차이에서 나온 값이다. 부모의 `children` Map 엔트리와 세그먼트 문자열을 포함한다.

### 3-2. 모델: 노드 객체 427 B, 그중 83%가 빈 컨테이너

`makeNode`(`path/index.ts:29`)는 빈 `Map`과 빈 `Set`을 **무조건 즉시** 할당한다. 자식도 구독자도 영영 안 생길 리프도 마찬가지다. 200k 샘플:

| 구성 | 노드당 |
|---|---|
| `makeNode`와 같은 모양 | **427 B** |
| 객체 필드만 (`segment`, `parent`) | 73 B |
| 빈 `Map` 하나 | 194 B |
| 빈 `Set` 하나 | 160 B |

427 B(모델)와 495 B(실제)의 차이는 부모 `children` 엔트리·문자열 몫으로 설명된다. 두 값은 상충하지 않는다.

**빈 컨테이너 둘이 354 B로 노드 객체의 83%다.** 이 사실은 `DC-13`의 후보 ①~⑤ 어디에도 없다. 필드를 지연 할당하면 리프가 427 → 73 B가 된다는 것은 위 표에서 따라 나오지만, **그 변경의 타당성·번들 영향(`DC-09` 잔여 132 B)·`readonly` 제약은 측정하지 않았다.** §6 참조.

## 4. 언제 쌓이고, 언제 비싼가

### 4-1. 위험 조건은 컴포넌트 churn이 아니라 경로 카디널리티다

트리는 구독자 단위가 아니라 **경로 단위**다. 노드 수 실측:

| 시나리오 | 노드 | 그중 구독 있는 노드 |
|---|---|---|
| A. `items[i]`에 10,000회 **쓰기만** | 10,003 | **1** |
| B. **서로 다른** 경로 10,000회 구독/해제 | 10,003 | 0 |
| C. **같은** 경로 10,000회 구독/해제 | **7** | 0 |

- **C**: 같은 컴포넌트를 10,000번 마운트/언마운트해도 노드는 7개다. `childOf`가 기존 노드를 재사용하므로 churn 자체는 트리를 키우지 않는다
- **A**: 10,002개는 `run`이 붙은 적이 **한 번도 없다.** 노드가 `.value`(구독)가 아니라 **프로퍼티 접근**에서 생기기 때문이다. `removeRun` 기반 정리를 검토할 때 이 행을 먼저 볼 것 — 그 경로로는 닿지 않는 노드들이다

> B의 누적 자체는 `tree-lifetime.ts`의 `keeps one node per distinct segment ever asked for`가 이미 고정한다. **A와 C의 대비는 고정돼 있지 않다.**

### 4-2. 쌓인 노드가 모든 쓰기를 느리게 하지는 않는다

100회 기준, 죽은 인덱스 노드 10,000개:

| 쓰기 모양 | 죽은 노드 10,000개 | 깨끗 |
|---|---|---|
| `items.value = [...]` (서브트리 DFS) | **13.3 ms** | 0.1 ms |
| `items.length = n` (형제 순회) | **9.7 ms** | 0.1 ms |
| `other.value = n` (무관한 필드) | 0.0 ms | 0.0 ms |

죽은 노드가 **영향 집합에 들어가는 모양의 쓰기만** 비용을 낸다. 서브트리 DFS가 더 비싼 것은 `pending` 스택(`path/index.ts:131`)이 노드를 전부 push/pop 하기 때문이다.

> `length` 쓰기가 죽은 형제를 순회한다는 사실은 `tree-lifetime.ts`의 `walks dead siblings on a length write`가 고정한다(방문 횟수 기준). **시간 비교와 서브트리 DFS 행은 고정돼 있지 않다.**

## 5. 후보별 보충 측정 (모델)

### 5-1. ⑤(구독 시점까지 노드 등록을 미룸)의 영향 집합 동등성

`DC-13` ⑤는 기록만 있고 검증이 없다. 영향 집합이 현행과 같은지를 `narrowing.ts`와 같은 차분 방식으로 확인했다.

쓰기 경로에 노드가 없을 수 있으므로, 존재하는 가장 깊은 조상까지 내려간 뒤 거기서부터 규칙을 적용하되 **"쓰려는 세그먼트"를 따로 넘기는** 형태가 된다. 각 대상의 근거:

| 대상 | 노드가 없을 때 |
|---|---|
| 자신 | 노드가 없으면 구독자도 없다 → 방문할 것이 없다 |
| 자손 | 구독이 체인을 통째로 실체화하므로, 자손이 있으면 자신도 있다 → 대우로 자신이 없으면 자손도 없다 |
| 조상 | 위에서 내려온 경로에 그대로 있다 |
| 형제 | **부모가 존재하면 세그먼트 기준 규칙을 그대로 적용해야 한다.** `items.2` 노드가 없어도 `items.length` 구독자는 통보받아야 한다 — `CI-21`이 놓쳤던 경로 |

결과 (무작위 구독 형태 × 무작위 쓰기 경로):

```
비교 3000건, 불일치 0건
```

형제 순회 비용(`length` 쓰기 200회, 인덱스 10,000개를 쓰기만 한 뒤): 현행 8.2 ms → ⑤ 모델 **0.0 ms**.

**측정한 것은 영향 집합의 동등성과 순회 비용뿐이다.** `DC-13` ⑤가 적은 유보("`childProxies`는 그대로이므로 메모리는 줄지 않는다")는 이 측정이 다루지 않으며, §2-2가 그 유보를 지지한다.

### 5-2. `deref` 비용 — ④의 하한선

`DC-13` ④가 "대가는 순회마다 deref"라고만 적은 부분의 수치다.

> **한계를 먼저 밝힌다.** ④는 `children`과 `childProxies`를 **둘 다** 약참조화하는 안인데, 아래 모델은 **`children`만** 약참조화했다. 그 절반짜리 구성은 `DC-13` ①이 이미 "아무것도 회수하지 못한다"고 기각한 모양이다. 따라서 아래는 **④의 측정이 아니라, ④가 치를 순회 비용의 하한선**이다.

`length` 쓰기 200회 / 인덱스 노드 10,000개:

| 상태 | 시간 | `children` 엔트리 |
|---|---|---|
| **GC 전** (참조는 죽었지만 미수거) | **55.2 ms** | 10,001 |
| GC 후 1회차 (순회가 죽은 엔트리를 지움) | 0.4 ms | 2 |
| GC 후 정상 상태 | 0.0 ms | 2 |
| *(참고) 현행* | *8.2 ms* | *10,001* |

전이되는 사실 둘:

- `deref()`는 평범한 Map 값 읽기의 **약 6.7배**(27.6 ns vs 4.1 ns)이고, `forEachAffectedNode`는 쓰기마다 도는 뜨거운 경로다
- 회수 시점이 **GC 타이밍에 의존**한다. GC가 아직 안 돈 구간이 존재하며, 그 구간의 비용은 결정적이지 않다

## 6. 측정하지 않은 것

다음에 이어서 할 때 여기부터 시작하면 된다.

- **노드 필드 지연 할당의 실제 영향.** §3-2는 "빈 컨테이너가 83%"라는 사실까지다. 번들 영향(`DC-09` 잔여 132 B), `children`/`subs`의 `readonly` 제약, 접근부 변경 범위는 미측정
- **④의 실제 비용.** §5-2는 절반 구성의 하한선이다. `children`+`childProxies` 양쪽 약참조화의 실제 수치, 그리고 `CI-15`(`ref.a === ref.a`) 보장이 실제로 어떻게 약해지는지는 미측정
- **⑤의 구현 형태.** §5-1은 영향 집합 동등성까지다. 프록시가 캐시한 노드를 어떻게 무효화할지(`INV`—프록시 수명 문제)는 설계도 측정도 없음
- **실사용 데이터.** `DC-13`이 재검토 조건으로 건 "실사용 보고"에 해당하는 것은 아직 없다

## 7. 재현

```js
// 노드 누적 — 배열이 줄어도 노드는 안 줄어든다
const watch = createStore({ items: [] });
const ref = watch();
for (let i = 0; i < 10000; i++) ref.items[i].value = i;
ref.items.value = [0, 1];                                   // 원소 2개, 노드 10,003개

watch(s => { s.items.length.value; });
for (let i = 0; i < 100; i++) ref.items.length.value = (i % 2) + 1;   // 9.7 ms (깨끗하면 0.1)
```

주의 두 가지:

- 같은 값을 반복해서 쓰면 `set` 트랩이 `value !== lensValue.get(rootValue)`에서 단락된다(`proxy/index.ts:225`). 벤치는 **매번 다른 값**으로 쓸 것
- `global.gc()`만 동기로 반복하면 회수가 반영되지 않는다. **호출 사이에 이벤트 루프를 한 번씩 돌릴 것**(`await new Promise(r => setTimeout(r, 1))`). 이걸 빠뜨려 §2-1을 한 번 잘못 측정했다
