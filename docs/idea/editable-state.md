# ref 기반 편집 기능과 차별화 방향

- 작성일: 2026-09-18
- 상태: 아이디어 검토. 구현 및 API 확정 전
- 배경: Zustand, Preact Signals, Jotai와 비교했을 때 state-ref를 선택할 구체적인 이유를 찾기 위한 논의
- 대상 사용자: 폼, 관리자 화면, 설정 화면, 문서·디자인 에디터를 만드는 개발자

## 1. 제안의 중심

가장 유망한 방향은 **아무 ref나 저장·취소·변경점 확인이 가능한 편집 대상으로 바꾸는 기능**이다. 이를 입력 컴포넌트, 일괄 편집, undo/redo와 연결한다.

목표는 다른 라이브러리로 구현할 수 없는 기능이라고 주장하는 것이 아니다. state-ref의 구조를 활용해 반복되는 편집 작업을 간결하고 일관된 API로 제공하는 것이다.

대표 메시지 후보:

> 어떤 중첩 상태든, 한 줄로 저장·취소 가능한 편집 화면으로.

이는 제품 방향에 대한 가설이다. 실제 코드량, 학습 부담, 오류 처리의 편리함은 시제품과 비교 예제로 검증해야 한다.

## 2. 현재 구조에서 활용할 수 있는 강점

| 현재 특성 | 편집 기능에 주는 이점 | 근거 |
|---|---|---|
| ref가 값 자체보다 상태 안의 경로를 가리킴 | 부모 객체를 교체해도 기존 ref로 그 경로의 최신 값을 읽고 쓸 수 있음 | [프록시 구현](../../packages/state-ref/src/proxy/index.ts) |
| 같은 ref에서 접근한 자식 프록시를 캐시함 | 입력 컴포넌트에 전달할 참조의 안정성을 활용할 수 있음 | [프록시 구현](../../packages/state-ref/src/proxy/index.ts) |
| `.value` 쓰기를 copy-on-write로 처리함 | 기존 상태와 편집 상태를 분리하고 변경되지 않은 구조를 공유하는 기반이 있음 | [Lens 구현](../../packages/state-ref/src/lens/index.ts) |
| 쓰기 시점에 대상 경로를 알고 있음 | 변경 기록, 경로별 충돌 확인, 범위를 지정한 이력 관리의 출발점이 있음 | [쓰기 처리](../../packages/state-ref/src/proxy/index.ts) |
| 경로별 구독과 프레임워크 커넥터가 있음 | 편집 기능의 코어를 공유하고 UI 연결부를 분리할 수 있음 | [경로 트리](../../packages/state-ref/src/path/index.ts), [React 커넥터](../../packages/connect-react/src/index.ts) |

참조의 안정성은 같은 참조 트리 안에서의 성질이다. 서로 다른 `watch` 호출이 반환한 ref까지 동일한 객체라는 의미는 아니다. 또한 배열의 인덱스 ref는 해당 위치를 가리키며, 특정 ID의 항목을 추적하는 기능은 별도 제안이다.

현재 `createStoreManualSync`는 변경 알림 시점을 제어한다. 원본과 분리된 초안이나 충돌을 확인하는 트랜잭션을 제공하지는 않는다. 현재 구현과 제안 기능을 구분해야 한다.

## 3. 경쟁 기능과 포지셔닝

2026-09-18 논의에서 확인한 공식 문서와 프로젝트 자료를 기준으로 한다. 아래는 유사 기능의 존재를 확인한 것이며, 전체 생태계에 같은 조합이 없다는 증거는 아니다.

| 비교 대상 | 이미 제공되는 관련 기능 | 제안에 주는 시사점 |
|---|---|---|
| [Zustand의 중첩 상태 갱신](https://zustand.docs.pmnd.rs/learn/guides/updating-state) | Immer, optics-ts 등을 이용한 중첩 갱신 | 깊은 값을 짧게 수정한다는 설명만으로는 차별점이 약함 |
| [Jotai의 focusAtom](https://jotai.org/docs/extensions/optics) | 일부 경로에 초점을 맞춘 읽기·쓰기 atom | 쓰기 가능한 부분 참조 자체를 독점 기능으로 볼 수 없음 |
| [Preact Signals](https://preactjs.com/guide/v10/signals/) | 자동 의존성 추적, computed, batch | 세밀한 반응성 자체를 대표 차별점으로 삼기 어려움 |
| [mobx-keystone의 Drafts](https://mobx-keystone.js.org/drafts/) | 초안, 저장·초기화, 경로별 저장과 수정 여부 확인 | 초안의 존재보다 ref에 적용하는 경험과 충돌 처리에 집중해야 함 |
| [Zundo](https://github.com/charkour/zundo) | Zustand용 undo/redo, 기록 대상 상태 선택 | undo/redo만으로 독점성을 주장하기 어려움 |
| [Jotai의 splitAtom](https://jotai.org/docs/utilities/split) | 배열 항목별 atom과 key extractor | ID를 활용한 항목 참조의 안정성에도 선행 기능이 있음 |

추천 포지셔닝은 **일반 객체의 아무 ref에나 편집 기능을 붙이고, 실제 상태·초안·일괄 편집을 일관된 방식으로 다루는 경험**이다. 이 조합이 경쟁 도구보다 얼마나 편리한지는 동일한 사용 시나리오로 비교해야 한다.

## 4. 기능 후보

아래 코드의 `fork`, `multi`, `createHistory`, `byKey` 및 UI 컴포넌트는 모두 제안 API다. 현재 패키지에서 가져와 실행할 수 있는 예제가 아니다. 예시의 `ref`는 기존 스토어에서 얻은 참조라고 가정한다.

### IDEA-01. 저장·취소 가능한 편집 세션

설정 모달이나 편집 폼에서 반복하는 임시 상태 생성, 원본 복사, 수정 여부 비교, 저장 시 병합을 담당한다.

```ts
// 제안 API
const draft = fork(ref.profile);

draft.ref.name.value = '새 이름';
draft.ref.address.city.value = '서울';

draft.dirty.value; // 이 편집 세션에 미반영 변경이 있는가?
draft.changes();   // 변경 경로와 이전/이후 값

const result = draft.commit(); // 저장 시 충돌 확인 후 반영
// 취소를 선택했다면 draft.discard()
```

핵심은 편집 도중 원본이 갱신되는 상황이다.

| 상황 | 목표 동작 |
|---|---|
| 사용자는 이름을 수정했고 서버 갱신은 전화번호를 변경함 | 저장 시 이름 변경과 최신 전화번호를 모두 유지 |
| 사용자와 서버 갱신이 같은 이름 필드를 서로 다르게 변경함 | 충돌을 반환하고 자동 덮어쓰기를 피함 |
| 사용자가 수정한 값을 편집 시작 시의 값으로 되돌림 | 해당 변경을 세션의 변경 목록에서 제거 |
| 사용자가 편집을 취소함 | 원본의 최신 상태를 유지하고 세션의 변경을 폐기 |
| 편집 중 원본의 상위 객체가 삭제되거나 다른 대상으로 교체됨 | 대상 유효성을 확인하고 정의된 오류 또는 충돌로 처리 |

차별화 후보는 일반 객체의 하위 ref에서 바로 시작할 수 있다는 점, 수정한 경로만 반영한다는 점, 충돌을 확인할 수 있다는 점의 조합이다. 단순 초안과 경로별 저장은 이미 [mobx-keystone에도 존재](https://mobx-keystone.js.org/drafts/)한다.

구현 시 검토할 사항:

- 편집 시작 값, 편집 값, 현재 원본을 비교하는 기준을 정의한다.
- 충돌 결과에 경로와 시작 값·편집 값·현재 값을 제공할지 결정한다.
- 다른 필드의 원본 갱신이 초안 화면에도 즉시 보일지, 저장할 때만 병합할지 결정한다.
- 부모 경로 교체와 자식 필드 수정처럼 경로가 겹치는 경우를 처리한다.
- `commit`의 전체 성공·전체 거부와 부분 반영 중 어떤 계약을 제공할지 결정한다. 첫 후보는 충돌 시 전체 반영을 거부하는 방식이다.
- 저장·폐기 이후 세션의 재사용 여부와 구독 해제 시점을 정한다.

최초 범위로는 일반 객체의 필드 편집이 적합하다. 배열은 전체를 하나의 변경·충돌 단위로 취급하고, 항목별 병합과 재정렬은 후속 검토한다.

### IDEA-02. ref 하나로 연결하는 입력 컴포넌트

필드의 값과 변경 함수를 각각 전달하는 작업을 줄이고, 중첩 상태에도 같은 입력 컴포넌트를 사용한다.

```tsx
// 제안 컴포넌트
<TextField field={ref.profile.name} />
<NumberField field={ref.profile.age} />
<Checkbox field={ref.settings.notifications} />

// 같은 컴포넌트로 초안 편집
<TextField field={draft.ref.name} />
```

복합 입력 컴포넌트에서 효과가 더 분명하다.

```tsx
// 제안 컴포넌트
<AddressEditor field={ref.customer.shippingAddress} />
<AddressEditor field={ref.company.officeAddress} />
<AddressEditor field={draft.ref.billingAddress} />
```

주소 편집기는 주소 데이터의 구조만 알면 된다. 상위 스토어 구조와 상태의 위치를 몰라도 내부 필드를 읽고 쓸 수 있는 경험을 목표로 한다.

확장 후보는 필드별 수정 여부, 오류, 초기화와 검증 어댑터다. 처음부터 완전한 폼 라이브러리를 만들기보다 독립적인 ref 구독 훅과 작은 바인딩 어댑터를 먼저 검토한다.

현재 ref에는 생성 시의 구독 문맥이 연결되어 있다. 임의의 ref를 전달받은 컴포넌트가 자기 수명에 맞춰 독립적으로 구독·해제할 수 있도록 연결 방식을 설계해야 한다. ref를 prop으로 전달하는 것만으로 이 동작이 이미 제공되는 것은 아니다.

숫자 입력의 빈 문자열, 파싱 실패, IME 입력, blur 시점의 반영처럼 입력 중 상태와 도메인 값이 다른 경우도 어댑터에서 다뤄야 한다.

### IDEA-03. 여러 항목을 하나의 필드처럼 편집

상품 여러 개의 가격을 수정하거나, 선택한 도형들의 색상을 변경하는 작업을 하나의 필드 인터페이스로 표현한다.

```ts
// 제안 API
const price = multi([
  ref.productsById.a.price,
  ref.productsById.b.price,
  ref.productsById.c.price,
]);

price.mixed.value; // 현재 값들이 서로 다른가?
price.value = 9900; // 선택한 상품 모두 변경
```

```tsx
// 제안 컴포넌트
<NumberField field={price} />
```

목표 흐름은 단일 필드 편집, 여러 필드 편집, 변경 미리보기, 일괄 저장·취소를 같은 입력 컴포넌트로 연결하는 것이다. 폼·관리자 도구·에디터에서 시각적으로 보여주기 좋은 후보다.

구현 시 검토할 사항:

- 값이 서로 다를 때 `.value` 읽기의 타입과 반환값을 정한다. `mixed` 표시만 추가한다고 문제가 모두 해결되지는 않는다.
- 빈 선택, 중복 ref, 읽기 전용 대상, 편집 중 선택 변경을 처리한다.
- 같은 스토어의 여러 쓰기를 하나의 편집 작업으로 반영하는 방법을 정한다.
- 일부 대상에서 쓰기가 실패할 때의 원자성을 정의한다.
- 초안과 결합하는 API 및 한 번의 undo로 되돌리는 범위를 설계한다.

첫 시제품은 하나의 스토어에 있는 `productsById` 같은 ID 기반 객체를 대상으로 한다. 여러 스토어 사이의 원자적 반영까지 최초 범위에 포함하지 않는다.

### IDEA-04. 하위 ref에 붙이는 undo/redo

이력을 관리할 범위를 ref로 지정한다.

```ts
// 제안 API
const history = createHistory(ref.document);

ref.document.title.value = '새 제목';
history.undo();
history.redo();
```

문서 내용을 되돌릴 때 메뉴, 로그인 상태, 다른 문서처럼 범위 밖의 상태는 유지한다. 드래그 중 발생한 여러 변경을 하나의 사용자 작업으로 묶는 기능도 후보에 포함한다.

[Zundo](https://github.com/charkour/zundo)도 undo/redo와 기록할 상태의 선택을 지원한다. 이 제안의 가치는 초안·일괄 편집과 연결되고, 임의의 하위 ref에 같은 방식으로 적용된다는 데 있다.

검토할 사항은 이력 크기 제한, 변경 묶기, undo 후 새 편집의 redo 처리, 외부 갱신의 기록 여부다. 같은 경로에 나중에 들어온 외부 변경을 어떻게 취급할지도 정의해야 한다. 범위가 있는 undo가 자동으로 협업 편집용 선택적 undo를 의미하지는 않는다.

### IDEA-05. 요청별 변경만 되돌리는 낙관적 업데이트

요청에 속한 변경을 기록하고, 실패했을 때 그 변경만 되돌리는 기능이다.

예시 시나리오:

1. 사용자가 주문 수량을 수정하고 저장 요청을 보낸다.
2. 요청을 기다리는 동안 배송 메모를 수정한다.
3. 수량 저장 요청이 실패한다.
4. 수량 변경의 복구를 검토하되 배송 메모는 유지한다.

같은 수량을 사용자가 다시 수정했다면 더 오래된 요청의 실패가 최신 입력을 덮어쓰면 안 된다. 경로별 버전 또는 작업 식별자를 사용해 이 요청이 만든 변경이 아직 현재 값에 해당하는지 판단해야 한다.

메시지 후보:

> 저장 실패가 사용자의 다음 입력을 지우지 않도록.

IDEA-01의 변경 기록과 충돌 처리 이후에 검토할 확장이다. 중첩된 요청, 응답 순서 역전, 서버가 값을 보정한 응답, 상위 객체 교체까지 고려해야 하므로 난도가 높다.

이 기능의 범위는 클라이언트 상태의 복구다. 서버에서 이미 발생한 작업의 취소나 네트워크 프로토콜 수준의 동시성 보장까지 제공하는 것은 아니다.

### IDEA-06. ID를 따라가는 배열 항목 ref

배열의 위치 대신 고유 키를 기준으로 특정 항목을 계속 가리킨다.

```ts
// 제안 API
const product = byKey(ref.products, {
  key: 'id',
  value: 'product-42',
});

product.price.value = 9900;
```

현재 `ref.items[3]`은 네 번째 위치를 가리킨다. 이 제안은 목록 재정렬이나 서버 응답으로 배열을 교체한 뒤에도 같은 ID를 가진 항목을 편집하는 경험을 목표로 한다.

[Jotai의 splitAtom](https://jotai.org/docs/utilities/split)에도 key extractor가 있다. 단독 대표 기능보다는 동적 목록에서 초안·일괄 편집을 지원하는 기반으로 평가한다.

ID 중복, 항목 삭제, ID 자체의 변경, 탐색 비용과 인덱스 갱신 비용을 검토해야 한다. 삭제된 항목의 ref를 통해 쓸 때 오류를 반환할지, 별도의 부재 상태를 표현할지도 정의해야 한다.

## 5. 구현 기반과 기존 계약

현재 코어에는 경로별 쓰기를 관찰할 내부 지점이 있지만, 제안에 필요한 공개 변경 기록·충돌 검사·독립 ref 구독 API는 없다. 기존 기능을 조합하는 것만으로 모든 제안이 완성되지는 않는다.

| 기반 과제 | 필요한 이유 |
|---|---|
| 임의의 ref를 독립적으로 구독·해제하는 방식 | 입력 컴포넌트와 확장 기능의 수명 관리 |
| 스토어 식별과 구조화된 경로 정보 | 동일 대상 판별, 경로 중첩 판단, 확장 기능 연결 |
| 쓰기 기록과 작업 단위 | 초안 변경점, 이력, 요청별 복구 |
| 변경 정규화 | 같은 경로를 여러 번 쓰거나 원래 값으로 되돌린 경우 처리 |
| 충돌 검사와 버전 관리 | 원본 갱신 및 늦게 도착한 요청 결과와 공존 |
| 명시적인 일괄 반영 | 여러 필드의 저장과 일괄 편집 |

구조화된 경로 정보는 디버그 문자열인 `NAVI`를 파싱하는 방식과 구분해야 한다. Symbol 키와 구분자가 포함된 키도 손실 없이 다룰 수 있어야 한다.

쓰기 기록의 전제도 명확히 해야 한다. `.value`로 받은 일반 객체를 직접 변경하는 작업은 프록시의 `.value` setter를 통과하지 않는다. 기록과 충돌 처리의 보장 범위는 지원하는 쓰기 경로를 기준으로 정의해야 한다.

기존 [코어 설계](../core-improvement/DESIGN.md)의 동기 전파 계약을 존중한다. 편집 기능을 위해 기본 쓰기에 암묵적인 microtask 지연을 도입하는 것은 이 제안에 포함하지 않는다. 별도 초안에서 다음 상태를 준비한 뒤 명시적 `commit`으로 동기 반영하는 방식을 먼저 검토한다. `createStoreManualSync`의 알림 지연만으로 격리나 원자성이 보장된다고 가정하지 않는다.

편집 기능은 선택적으로 가져오는 확장 패키지로 제공하는 구성을 우선 검토한다. 코어에는 필요한 최소 연결 지점을 두고, 패키지 경계와 이름은 후속 설계에서 결정한다.

## 6. 추천 검토 순서

이는 추천 순서이며 확정된 개발 일정이 아니다.

1. 임의의 ref 구독과 변경 기록에 필요한 연결 지점을 검토한다.
2. IDEA-01의 일반 객체 편집, 변경점 확인, 충돌 확인 후 저장·취소를 시제품으로 만든다.
3. IDEA-02로 실제 상태와 초안에 같은 입력 컴포넌트를 연결한다.
4. IDEA-03을 같은 스토어의 ID 기반 객체에 적용해 일괄 편집을 시연한다.
5. IDEA-04를 확장하고, 배열 편집 요구가 생기는 시점에 IDEA-06을 검토한다.
6. 변경 기록과 충돌 처리의 계약이 안정된 뒤 IDEA-05를 검토한다.

첫 대표 기능은 IDEA-01, 편리함을 보여줄 조합은 IDEA-01 + IDEA-02 + IDEA-03을 추천한다.

## 7. 첫 홍보 데모

상품 세 개의 가격을 일괄 편집하는 관리자 화면을 만든다. 최초 데이터는 ID 기반 객체로 구성해 배열 재정렬 문제와 분리한다.

1. 상품 세 개를 선택한다. 가격이 다르면 입력창에 혼합 상태를 표시한다.
2. 가격을 입력해 편집 중인 값과 변경 내용을 미리 보여준다.
3. 편집 중 서버 갱신을 흉내 내어 원본의 재고를 변경한다.
4. 저장하면 새 가격과 최신 재고가 모두 남는 모습을 보여준다.
5. 별도 실행에서는 취소해 가격 변경이 폐기되고 최신 재고는 유지되는 모습을 보여준다.
6. 같은 가격 필드에 원본 갱신이 들어오는 경우에는 충돌을 표시한다.
7. 화면 아래에 이 동작을 구성한 코드를 함께 보여준다.

평가할 내용은 단순한 코드 줄 수뿐 아니라 원본·초안·변경 여부를 따로 관리하는 부담, 입력 컴포넌트 재사용성, 충돌 처리의 명확성이다. 경쟁 도구로 같은 시나리오를 만든 예제와 비교해 편의성을 검증한다.

## 8. 다음 설계에서 결정할 질문

- 편집 세션의 변경 여부는 시작 스냅샷과 어떤 동등성 기준으로 비교하는가?
- 수정하지 않은 필드의 원본 변경을 초안 화면에 실시간 반영하는가?
- 같은 값으로 수렴한 동시 변경은 충돌 없이 처리하는가?
- 부모 교체와 자식 수정이 겹칠 때의 충돌 범위는 어디까지인가?
- `commit` 성공·충돌·대상 소멸을 어떤 반환 타입으로 표현하는가?
- 초안의 저장은 로컬 스토어 반영이며, 서버 저장 성공과는 어떻게 연결하는가?
- ref 구독, UI 어댑터, 편집 확장 사이의 공개 인터페이스는 무엇인가?
- 최초 지원 데이터 범위와 배열·Map·Set 등 후속 지원 범위는 어디까지인가?

이 문서는 기능 후보와 제품 방향을 보존하기 위한 기록이다. 실제 채택 시에는 선택한 범위의 요구사항, API 계약, 검증 시나리오를 별도 설계로 구체화한다.
