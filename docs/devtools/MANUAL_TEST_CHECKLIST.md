# MANUAL_TEST_CHECKLIST — state-ref DevTools

- 작성일: 2026-10-24. 상태: 전 항목 미수행. 구현 전 계획이다.
- 브랜치: `feat/state-ref-devtools`. 조사 기준 commit: `412db01a63321eef3087f3bc04c46708447a29f8`.
- 연계: [REQUIREMENTS](./REQUIREMENTS.md), [DESIGN](./DESIGN.md), [IMPLEMENT](./IMPLEMENT.md).
- 실제 브라우저의 DOM 단언은 자동 검증 증거로 적을 수 있다. 사람이 확인할 가독성·focus·heap 판단을 대신 완료 표시하지 않는다.
- Phase 0의 Node 실험은 이 체크리스트의 패널·브라우저·가독성 통과 증거가 아니다. 해당 결과는 IMPLEMENT에 별도 기록한다.

## 실행 전 기록

- 검사할 구현 commit/dirty 여부, Node/pnpm, OS·브라우저 버전, 예제 주소, DevTools 설정과 한도를 기록한다.
- 초기화한 테스트 앱에 core store 두 개, 같은 key를 사용하는 Sync client 두 개, 실제 요청 횟수 계측을 준비한다. 실제 업무 데이터가 아닌 fixture를 쓴다.
- 앱 자체의 구독·요청 수를 따로 계측한다. 패널이 보여주는 숫자만 읽어 패널이 맞다고 판단하지 않는다.
- 아래 절차의 버튼·fixture는 구현 단계에서 생성한다. 현재 실행 가능한 데모 주소나 구현 완료 기능으로 해석하지 않는다.

## M-DT-01 — 연결과 기본 사용

관련: R-DT-01/07, DC-DT-01/03/10, T-DT-01/11.

- [ ] 개발 예제를 열고 패널을 연결한다. 이름이 같은 두 store가 서로 다른 ID로 보이는지 확인한다.
- [ ] 한 store를 선택하고 앱에서 값을 바꾼다. 선택한 대상의 상태·이력만 해당 변경을 보여야 한다.
- [ ] 등록하지 않은 store는 자동으로 나타나지 않는다. 미지원 watch 또는 버전은 명확한 진단으로 보인다.
- [ ] 연결 코드와 종료 코드가 짧고, 기존 `createStore` 사용법을 교체할 필요가 없는지 가이드를 따라 확인한다.
- [ ] 개발 조건을 끈 기본 코어, 3.2.x 구버전, protocol mismatch에서 각각 개발 조건/버전/원래 watch에 대한 안내가 실제 해결 방법과 일치하는지 확인한다.

통과: 연결·대상 구분·해제 절차를 가이드만으로 수행한다. 실패: 이름이 같다고 다른 store를 합치거나, 연결을 위해 앱 상태관리 코드를 재작성해야 한다.

## M-DT-02 — 현재 값과 경로 탐색

관련: R-DT-02/09, DC-DT-06, T-DT-05.

- [ ] primitive root, 중첩 객체, 배열, 점이 들어간 key, 같은 설명의 symbol 두 개를 각각 탐색한다.
- [ ] `undefined`, 없는 경로, 생략된 값, 마스킹된 값이 같은 빈칸으로 보이지 않는지 확인한다.
- [ ] 긴 문자열·큰 배열·깊은 트리·순환 값의 표시 한도와 생략 안내를 확인한다.
- [ ] getter 호출 카운터 fixture를 펼쳐 도구 때문에 getter가 실행되지 않는지 확인한다. 지원하지 않는 객체는 실행/열거를 강요하지 않고 표식으로 보인다.

통과: 대상 값과 경로를 오해하지 않고 앱 구독/부수효과 수가 늘지 않는다. 실패: 다른 symbol이 같은 경로로 합쳐지거나 도구의 탐색으로 앱이 달라진다.

## M-DT-03 — 변경 이력·batch·manual-sync

관련: R-DT-03/04, DC-DT-04/05, T-DT-02~04.

- [ ] 같은 경로를 `A → B → C`로 연속 변경하고 첫 이벤트를 선택한다. 첫 이벤트의 before/after는 계속 A/B다.
- [ ] 동일값 대입과 거절되는 쓰기를 실행한다. 성공한 변경 이력에는 추가되지 않는다.
- [ ] batch에서 세 번 쓰고, 앱 callback 수와 패널의 쓰기 수·batch 묶음을 각각 확인한다.
- [ ] manual-sync에서 값을 바꾸고 sync 전/후를 비교한다. 현재값/쓰기 기록과 callback 실행의 시점이 구분돼야 한다.
- [ ] 구독 callback이 다른 값을 쓰는 fixture, callback이 예외를 던지는 fixture에서 commit 순서와 앱의 결과를 비교한다.
- [ ] 과거 이벤트를 선택하거나 clear를 눌러도 실제 앱 값과 서버 요청 수가 바뀌지 않는다.

통과: 각 성공한 쓰기와 실제 알림을 구분할 수 있다. 실패: 최종 값만 남겨 중간 쓰기가 없었던 것처럼 보이거나 과거 선택으로 상태가 복원된다.

## M-DT-04 — 구독 경로와 실행 이유

관련: R-DT-05, DC-DT-08, T-DT-06/13.

- [ ] A는 `user.name`, B는 `user.age`를 읽는 fixture에서 name만 변경한다. A의 update 실행만 증가한다.
- [ ] 조건부 읽기를 가진 구독으로 `trackDeps` off/on을 각각 확인한다. 패널은 해당 모드의 실제 dependency 집합을 보여야 한다.
- [ ] 부모 가지 교체·배열 length 변경·구독 중 다른 구독 해제를 확인한다. 실행 후보와 실제 실행을 혼동하지 않는다.
- [ ] AbortSignal/`false`로 종료하고 남겨둔 ref를 다시 읽는다. 종료한 구독이 패널 또는 앱에서 되살아나지 않는다.
- [ ] React StrictMode나 부모 rerender가 있는 예제에서 패널 수치를 실제 렌더 횟수로 읽게 만드는 문구가 없는지 확인한다.

통과: '어떤 경로 때문에 어느 구독이 실행됐는가'를 설명할 수 있고 미상 원인은 미상으로 보인다. 실패: 모든 subscriber가 실행됐다고 기록하거나 컴포넌트명을 추정해 붙인다.

## M-DT-05 — Sync 캐시·mutation 관측

관련: R-DT-06, DC-DT-09, T-DT-07.

- [ ] 같은 query key를 가진 client 둘을 선택해 별도 캐시·작업 목록을 확인한다.
- [ ] load/retry·scope 대기·mutation 완료를 실행하고 phase/attempt/linkedKeys를 실제 fixture 흐름과 대조한다.
- [ ] 완료한 작업이 현재 작업 목록에서 빠지고 도구의 종료 이력에만 남는지 확인한다.
- [ ] 마지막 handle을 해제해 owners가 0이 돼도 GC 전 캐시가 남는 것을 확인한다. 패널은 이를 누수나 삭제로 표시하지 않는다.
- [ ] 패널을 열고 닫거나 탭을 바꿔도 queryFn·mutation 호출 횟수와 owners가 증가하지 않는다.
- [ ] query 데이터·mutation 입력·오류 원문이 제공되는 것처럼 보이지 않는지 확인한다. unknown/sync-error에 자동 재전송 버튼을 제공하지 않는다.

통과: 현재 공개 메타데이터만으로 정확한 상태를 전달한다. 실패: 관측이 앱 요청/소유권을 바꾸거나 success 표시를 서버 성공 확인으로 안내한다.

## M-DT-06 — 오래 사용하기와 종료

관련: R-DT-08/09, C-DT-05, DC-DT-03/07/12, T-DT-08~10.

- [ ] 10,000회 변경 fixture에서 한도에 닿았을 때 오래된 이력 제거·queue gap·현재 상태 재조회가 표시되는지 확인한다.
- [ ] pause 중 앱을 변경하고 resume한다. 이력이 없는 구간과 새 현재값을 구분할 수 있어야 한다.
- [ ] 접기·펼치기와 mount/unmount를 20회 반복한다. 접기는 기록 유지, unmount는 panel 자원 해제라는 차이가 안내돼야 한다.
- [ ] detach와 tools.dispose 뒤 앱 조작을 계속한다. 앱은 정상 동작하고 제거된 도구의 이벤트·timer·DOM은 되살아나지 않는다.
- [ ] HMR 후 이벤트가 중복되지 않는지 확인한다. heap snapshot에서 dispose한 session이 이전 store/버퍼를 계속 붙드는 경로를 살핀다.

통과: phase 0에서 정한 비용 기준과 명시적 수명 계약을 만족한다. 실패: 길게 쓸수록 이력/queue/DOM이 무제한 증가하거나 해제 뒤 대상이 유지된다. JS heap 수치는 Preview의 byte 한도와 같다고 판단하지 않는다.

## M-DT-07 — 표시 데이터 경계

관련: R-DT-09, C-DT-07, DC-DT-06/07, T-DT-05/08.

- [ ] 마스킹 설정한 fixture 값을 현재 탭·before/after·검색·진단에서 찾아 원문이 없는지 확인한다.
- [ ] DevTools를 조작하면서 Network와 Storage를 확인한다. 앱 원래 요청 외 도구의 자동 전송과 상태 영속 저장이 없어야 한다.
- [ ] 값 표시 실패가 나는 fixture에서도 다른 store 관측과 앱의 쓰기는 계속 동작한다.

통과: 문서에 선언한 데이터 경계가 실제 관측 경로 전체에 적용된다. 실패: 화면만 가리고 이력이나 검색 데이터에 원문을 남긴다.

## M-DT-08 — 접근성·프레임워크·가이드

관련: U-DT-05, R-DT-07, C-DT-06/08, DC-DT-01/02/10, T-DT-11~14.

- [ ] 키보드만으로 열기·탭 이동·검색·이력 선택·닫기를 수행한다. focus 이동과 복귀가 자연스럽고 앱으로 돌아갈 수 있는지 사람이 확인한다.
- [ ] 작은 viewport, 긴 한국어 이름/값, 확대 화면, 강한 전역 CSS가 있는 앱에서 내용과 조작이 겹치지 않는지 확인한다.
- [ ] React/Preact/Vue/Svelte/Solid/Lithent별로 동일한 연결·해제 절차를 수행한다. 프레임워크마다 성공 여부를 따로 기록한다.
- [ ] SSR 앱에서 import 오류가 없고 client mount 후에만 패널이 생기는지 확인한다.
- [ ] 개발용 조건부 연결을 따른 production 예제에서 패널·도구 코드·불필요한 listener가 없는지 자동 artifact 검사 결과와 대조한다.
- [ ] `development` 조건의 core와 batch가 함께 선택되는지 확인한다. Vite 외 지원 bundler와 Node `--conditions=development`의 설치 안내를 구분하고, production에서 조건을 강제하지 않도록 설명한다.
- [ ] 가이드만 보고 설치/연결/종료할 수 있는지 확인한다. 아직 없는 타임트래블·stack trace·Redux 연동을 지원한다고 읽히는 표현이 없어야 한다.

통과: 지원 대상과 사용법이 실제 배포 산출물·사용 경험과 일치한다. 실패: 5종 테스트만으로 6종 지원을 주장하거나 DOM 없는 환경에서 import가 깨진다.
