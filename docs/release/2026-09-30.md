# 2026-09-30 배포 절차

패키지 7개를 npm에 올린다. 이 문서의 명령을 위에서부터 차례로 실행하면 된다.

준비 상태(2026-09-29 기준):

- `package.json`의 버전과 peer 범위는 이미 고쳐서 브랜치 `feat/server-sync-draft`에 커밋해 두었다.
- `CHANGELOG.md`의 각 절에서 `(unreleased)` 표시를 뗐다.
- 7개 모두 `pnpm publish --dry-run`을 통과했다.

## 무엇을 올리나

| 순서 | 패키지 | npm에 있는 버전 | 올릴 버전 | 성격 |
|---|---|---|---|---|
| 1 | `state-ref` | 3.0.2 | **3.1.0** | 기능 추가(draft·batch·plugin 진입점), CI-30 수정 |
| 2 | `@stateref/sync` | 없음 | **0.1.0** | **첫 배포**. ESM 전용 |
| 3 | `@stateref/connect-react` | 18.3.0 | **19.0.0** | `useSyncExternalStore`, React 18·19 지원 |
| 4 | `@stateref/connect-preact` | 10.3.0 | **10.4.0** | 커밋 뒤 구독 |
| 5 | `@stateref/connect-vue` | 3.3.0 | **3.4.0** | 선택값 readonly(동작 변경), `vue ^3.2.0` |
| 6 | `@stateref/connect-svelte` | 4.3.0 | **5.0.0** | Svelte 4·5 지원, `./runes` 진입점 추가 |
| 7 | `@stateref/connect-solid` | 1.3.0 | **1.4.0** | 얼린 복사본(동작 변경), setter 직접 쓰기 |

**순서가 중요한 이유:** 나머지 6개가 모두 peer로 `state-ref ^3.1.0`을 요구한다. 코어를 먼저 올리지 않으면, 그 사이에 커넥터를 설치한 사람은 peer를 풀지 못한다. 커넥터 5개(3~7)끼리는 서로 의존하지 않으므로 순서가 상관없다.

**이번에 같이 바뀐 것:**

- 커넥터 5개의 `state-ref` peer를 `^3.0.0`에서 `^3.1.0`으로 올렸다. 커넥터는 3.1.0에서만 테스트했고, 3.1.0의 CI-30 수정(끝낸 구독이 다시 살아나지 않음)이 커넥터의 구독 해제·재구독에 영향을 준다.
- `@stateref/sync`의 peer는 `^3.0.2`에서 `^3.1.0`으로 올렸다. sync는 3.1.0에 새로 생긴 `state-ref/plugin`·`draft`·`batch`를 쓴다.
- 커넥터 5개의 배포 파일에서 `src/tests`를 뺐다(`"!src/tests"`). 코어는 이미 이렇게 하고 있었다. 예를 들어 connect-vue 묶음이 44개 파일에서 13개로 줄었다.

## 0. 준비 (한 번만)


npm 계정에 2단계 인증이 켜져 있으면, 각 `pnpm publish` 명령에 `--otp=123456`(인증 앱의 6자리)을 붙이거나 명령이 물어볼 때 입력한다.

## 1. main에 합치기

지금까지의 배포 태그는 main의 커밋을 가리킨다. 3.0.2는 `a476d0a`이다. 이번 배포도 main에서 한다.

현재 브랜치는 main 위에 커밋 170여 개를 얹은 상태이고(2026-09-29 기준 173개), main 쪽에만 있는 커밋은 0개다. 그래서 충돌 없이 fast-forward된다.

- **PR로 합칠 때:** GitHub에서 `feat/server-sync-draft` → `main` PR을 만들어 머지한다.
- **직접 합칠 때:**

```bash
git fetch origin
git checkout main
git pull --ff-only origin main
git merge --ff-only origin/feat/server-sync-draft
git push origin main
```

`pnpm publish`는 기본값으로 main 브랜치의 깨끗한 작업 트리에서만 동작한다. 브랜치가 다르거나 커밋 안 된 파일이 있으면 `ERR_PNPM_GIT_UNCLEAN` 같은 오류로 멈춘다. 그러니 이후 단계는 main에서 한다.

## 2. 깨끗하게 설치하고 빌드

```bash
pnpm install --frozen-lockfile
pnpm build          # 코어 → 나머지 → 선언 파일 보정(fix-declarations) → skills 복사
```

**반드시 루트의 `pnpm build`를 쓴다.** 패키지마다 `vite build`만 하면 `scripts/fix-declarations.mjs`가 돌지 않는다. 그러면 `.d.ts`의 상대 import에 `.js`가 붙지 않고 `.d.cts`도 생기지 않는다(Phase 7.3에서 고친 배포 결함).

## 5. 배포 (이 순서로)

`pnpm publish`를 쓴다(`npm publish`가 아니다). devDependencies의 `workspace:*`를 실제 버전으로 바꿔 주는 것이 pnpm이기 때문이다.

scoped 패키지(`@stateref/*`)는 첫 배포 때 기본값이 비공개다. 그래서 `--access public`을 붙인다. 이미 공개된 패키지에 붙여도 해가 없으므로 전부 붙인다.

```bash
# 1) 코어 — 반드시 먼저
cd packages/state-ref && pnpm publish && cd ../..
npm view state-ref version                 # 3.1.0 이 나오면 다음으로

# 2) sync — 첫 배포라 --access public 필수
cd packages/sync && pnpm publish --access public && cd ../..
npm view @stateref/sync version            # 0.1.0

# 3) 커넥터 5개 — 순서 무관
cd packages/connect-react  && pnpm publish --access public && cd ../..
cd packages/connect-preact && pnpm publish --access public && cd ../..
cd packages/connect-vue    && pnpm publish --access public && cd ../..
cd packages/connect-svelte && pnpm publish --access public && cd ../..
cd packages/connect-solid  && pnpm publish --access public && cd ../..
```

한 번에 올리는 방법도 있다. 아래 명령은 워크스페이스에서 아직 npm에 없는 버전만 의존 순서대로 올린다. 예제와 문서 사이트는 `private`이라 건너뛴다. 다만 중간에 실패하면 어디까지 올라갔는지 따로 확인해야 하므로, 위의 하나씩 올리는 방법을 권장한다.

```bash
pnpm -r publish --access public
```

## 문제가 생기면

| 증상 | 원인과 대처 |
|---|---|
| `E403 You cannot publish over the previously published versions` | 이미 올라간 버전이다. `npm view <이름> version`으로 확인하고 다음 패키지로 넘어간다. |
| `E402 Payment Required` / `You must sign up for private packages` | scoped 패키지에 `--access public`을 빠뜨렸다. |
| `EOTP` | 2단계 인증 코드가 필요하다. `--otp=XXXXXX`를 붙인다. |
| `ERR_PNPM_GIT_UNCLEAN` / `ERR_PNPM_GIT_NOT_CORRECT_BRANCH` | main이 아니거나 커밋 안 된 변경이 있다. `git status`로 확인한다(빌드 산출물 `dist`는 git이 무시한다). |
| 설치 시 `peer state-ref@^3.1.0` 경고 | 코어 3.1.0보다 커넥터가 먼저 올라갔다. 코어를 올리면 풀린다. |
| gate가 `bench`에서만 실패(예: `1000 live index nodes ... (target <= 5 ms) FAIL`) | 실제 시간을 재는 단계라 기계 부하에 흔들린다. 2026-09-30 재시작한 컨테이너에서는 코어 코드가 같은데도 4.6~9.7 ms가 나왔고 세 번 중 한 번 통과했다. `node packages/state-ref/bench/read-write.mjs`만 다시 돌려 본다. 조용한 기계에서도 계속 넘으면 배포를 멈추고 원인을 본다. 나머지 단계가 전부 pass인지도 확인한다. |
| 잘못된 내용을 올렸다 | 같은 버전은 다시 올릴 수 없다. 고친 뒤 패치 버전을 올려 다시 배포하고, 잘못된 버전은 `npm deprecate <이름>@<버전> "use <새 버전>"`으로 표시한다. `npm unpublish`는 72시간 안에만 가능하고, 그 버전 번호는 다시 쓸 수 없다. |
