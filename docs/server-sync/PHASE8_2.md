# Phase 8.2 — 두 소비자·Draft 2개·Metadata와 수명

**진입:** [Phase 8.1](./PHASE8_1.md) 종료, 전체 gate 통과.
**범위:** 한 client의 두 소비자, 독립 draft 2개, `inspectCache()` 기반 metadata 표시, mount/unmount 수명. 8.1에서 발견한 **Svelte 커넥터의 쓰기 되돌림 미해제**를 반례로 고정한 뒤 고친다. M2-03과 M2-20의 자동 부분.
**종료:** 네 시나리오가 5종에서 같은 의미로 동작하고, Svelte 결함이 반례와 함께 수정되며, 전체 gate 통과.

## 8.1에서 넘어온 결함

[Phase 8.1](./PHASE8_1.md)의 탐색 중 `connectSvelte`만 파괴 뒤 동작이 다른 것을 측정했다.

| 파괴 뒤 | 원본 → UI (watch) | UI → 원본 (쓰기 되돌림) |
| --- | --- | --- |
| React·Preact | 끊김 | 별도 구독 없음 |
| Vue | 끊김 | 끊김 (`watch()`가 setup 소유) |
| Solid | 끊김 | 끊김 (`createEffect`가 컴포넌트 root 소유) |
| **Svelte** | 끊김 | **살아 있음 — 원본에 써진다** |

`connectSvelte`의 `onDestroy`는 `abortController.abort()`로 watch 구독만 정리하고, 자신이 만든 `signalValue.subscribe(...)`의 해제 함수는 버린다. Svelte는 마크업의 `$store` 자동 구독만 정리하고 수동 `.subscribe()`는 정리해 주지 않으므로, 다른 셋과 달리 소유자가 없다. 파괴된 컴포넌트의 스토어에 누군가 쓰면 그대로 원본까지 써지고, sync 맥락이라면 해제된 query를 건드려 [Phase 8.1](./PHASE8_1.md)의 unhandled error 경로를 탄다.

영향 범위는 작다 — 스토어는 컴포넌트 init에서 만들어져 보통 파괴와 함께 도달 불가능해진다. 그래도 계약이 5종에서 갈리는 것 자체가 결함이므로 고친다.

## 요구와 결정

- [x] **DC8-2-01 / 끊어야 하는 것은 "미러"를 가진 커넥터의 쓰기 되돌림뿐이다:** 계획 단계에서는 "파괴 뒤 쓰기가 원본에 닿지 않는다"를 5종 공통 계약으로 적었으나, 확인해 보니 **틀렸다.** Vue·Svelte·Solid는 프레임워크 소유의 미러(`reactive`/`writable`/`signal`)를 만들고 그것을 원본에 되돌려 쓰는 구독을 갖는다 — 이 구독은 컴포넌트와 함께 죽어야 한다. React·Preact는 미러가 없고 hook이 **원본 ref 자체**를 돌려주므로, 파괴 뒤에도 그 ref로 쓰면 당연히 원본에 써진다(측정으로 확인). 그것은 누수가 아니라 다른 참조를 하나 들고 있는 것과 같으며 커넥터가 개입할 지점이 아니다. 따라서 반례는 두 종류로 나뉜다: 미러가 있는 셋은 **끊김**을, 없는 둘은 **ref가 원본 그대로임**을 고정한다.
- [x] **DC8-2-01b / Svelte 수정은 두 부분이다:** 반례로 실패를 먼저 확인한 뒤 고쳤다. (1) `signalValue.subscribe(...)`의 해제 함수를 `onDestroy`에 연결한다. (2) **구독자 본문 전체를 예외로부터 격리한다** — 아래 [더 심각한 결함](#더-심각한-결함-전역-스토어-큐-오염) 때문이다. 비교와 대입 둘 다 거절될 수 있으므로(폐기된 draft나 해제된 query는 **읽기도** 던진다) 대입만이 아니라 구독자 전체를 감싼다.
- [x] **DC8-2-02 / IC-01과 구분:** core-improvement의 `IC-01`(`unmount-leak.tsx`)은 **watch 구독**의 해제를 다루고 그 경로는 5종 모두 정상이다. 여기서 고치는 것은 커넥터가 자기 프레임워크 쪽에 만든 **쓰기 되돌림 구독**이다. 두 문서를 섞지 않는다.
- [x] **DC8-2-03 / 두 소비자의 공유와 격리:** 같은 client·같은 key를 보는 두 컴포넌트는 기준과 편집을 공유하고, 한쪽의 편집이 다른 쪽에 보이며, 그것만으로 WRITE는 일어나지 않는다. 한 소비자의 언마운트가 다른 소비자의 구독이나 query를 해제하지 않는다 — 소유권은 `dispose()`를 부르는 소유자에게 있다([DC5-05-03](./PHASE5_5.md)).
- [x] **DC8-2-04 / 독립 draft 2개:** 한 원본에서 만든 draft 2개는 입력이 서로 섞이지 않고 각자의 `changes`·`conflicts`를 갖는다. 한쪽의 apply는 다른 쪽에 원본 갱신으로 도착하며, 겹친 경로는 conflict가 된다([Phase 6](./PHASE6.md)).
- [x] **DC8-2-05 / metadata 관측:** UI가 보는 metadata는 `inspectCache()`/`subscribeCache()`뿐이고 query payload나 편집 값을 끌어오지 않는다([Phase 5.12](./PHASE5_12.md)). [Phase 7.4](./PHASE7_4.md)의 보존 사유 네 가지(`owners`·`dirty`·`unconfirmed`·`pending`)가 **UI 수명 주기에서도 같은 값으로 관측**되는지가 이 단계의 핵심 확인이다. `owners`는 **handle 수를 따르고 컴포넌트 수를 따르지 않는다** — 같은 key로 handle 2개를 열면 2, 하나를 해제하면 1임을 확인했다. 한 handle을 두 컴포넌트가 공유하면 `owners`는 1이고, 컴포넌트가 언마운트해도 내려가지 않는다.
- [x] **DC8-2-06 / 차이:** 조회와 다른 DTO·제출 중 추가 입력·기준 복구 실패는 8.3, SSR 격리와 loading/error는 8.4다. 이 단계는 한 client 안의 소비자 구성만 본다. **metadata를 화면에 그리는 패널 자체는 만들지 않았다** — `inspectCache()`의 값을 UI 수명 주기 안에서 확인하는 데까지만 했고, 실제 metadata 패널은 [Phase 8](./PHASE8.md) 8.5의 `examples/` 데모에 속한다.

## 구현 단계와 기준 테스트

1. **파괴 뒤 쓰기 경로:** 반례를 먼저 쓴다. **기준 테스트:** Vue·Svelte·Solid는 파괴 뒤 미러에 써도 원본이 변하지 않는다. React·Preact는 held ref가 원본 그대로임을 고정한다. 이 시점에 **Svelte만 실패**해야 한다(실패하지 않으면 반례가 틀린 것이다).
2. **수정:** `connectSvelte`의 쓰기 되돌림 구독을 `onDestroy`에 연결한다. **기준 테스트:** 1번이 5종 모두 통과하고, 기존 Svelte 테스트 18개와 `integration.test.ts`의 렌더 계약이 그대로다.
3. **두 소비자:** 같은 key의 컴포넌트 2개. **기준 테스트:** 기준·편집 공유, WRITE 0회, 한쪽 언마운트 뒤에도 다른 쪽이 계속 갱신되고 `client.size()`가 줄지 않음.
4. **독립 draft 2개:** 한 원본에서 draft 2개. **기준 테스트:** 입력 격리, 한쪽 apply가 다른 쪽에 원본 갱신으로 도착, 겹친 경로의 conflict.
5. **metadata:** `inspectCache()`를 UI에 표시. **기준 테스트:** `owners`가 handle 수를 따르고 컴포넌트 수를 따르지 않음, 편집이 `dirty`로 보임, 관측 경로에 payload가 없음.
6. **검증력:** 결함 주입으로 각 반례가 실제로 잡는지 확인한다.
7. **통합:** 5종 패키지 테스트와 `pnpm gate`; canonical 문서와 인계를 갱신한다.

## 구현 전 탐색 결과

- `owners`는 handle 수를 따른다(1 → 2 → 1). DC8-2-05를 그에 맞춰 확정했다.
- React의 held ref는 언마운트 뒤에도 원본에 쓴다. DC8-2-01의 처음 문장이 틀렸음을 여기서 잡았고, 계약을 미러 유무로 갈라 다시 적었다.
- 남은 확인: Svelte 수정이 `integration.test.ts`의 렌더 횟수 계약(core-improvement Phase 8)에 영향을 주는지. 영향이 있으면 그쪽 문서와 함께 다뤄야 한다.

## 더 심각한 결함: 전역 스토어 큐 오염

해제 계약을 반례로 쓰다가 그 반례가 **첫 단언부터** 실패했다. 마운트된 상태의 쓰기조차 원본에 닿지 않았는데, 같은 코드를 단독 파일에서 돌리면 통과했다. 원인은 순서 의존이었다.

Svelte 4의 `writable.set`은 전역 `subscriber_queue`에 구독자를 쌓고 한 번에 flush한 뒤 `subscriber_queue.length = 0`으로 비운다. **flush 도중 구독자가 예외를 던지면 그 비우기에 도달하지 못한다.** 이후 모든 `set`은 "이미 flush 중"으로 판단해 큐에 쌓기만 하고 아무에게도 알리지 않는다. 측정한 결과:

| 단계 | 관측 |
| --- | --- |
| 예외 전, 무관한 스토어 | 정상 알림 |
| 해제된 query에 쓰기 | 거절 예외 |
| 예외 후, 같은 무관한 스토어 | **알림 멈춤** |
| 예외 후, 새로 만든 스토어 | **알림 멈춤** |

즉 커넥터의 쓰기 되돌림에서 예외 하나가 나면 **앱 전체의 Svelte 스토어가 조용히 죽는다.** 실패는 예외가 난 곳이 아니라 한참 뒤 무관한 곳에서 드러나므로 원인을 찾기 어렵다. 테스트에서는 한 테스트가 뒤 테스트들을 깨뜨리는 순서 의존으로 나타난다.

`set`이 예외 안전하지 않은 것은 Svelte 쪽이라 고칠 수 없다. 고칠 수 있는 것은 **던질 수 있는 코드를 스토어 구독자 안에 넣은 쪽**, 즉 우리 커넥터다. 거절은 삼키지 않고 `reportError`로 — 없으면 `error` 이벤트로, 그것도 없으면 타이머로 — 밖에서 보고한다. 결과적으로 다른 네 커넥터와 같은 표면(uncaught error)이 되고, 호출 지점으로 돌아오지 않는다는 [Phase 8.1](./PHASE8_1.md)의 계약도 유지된다.

5종에 반례 **11개**를 더했다(해제 3, 큐 안전 1, held ref 2, 두 소비자·draft 2개 5). 8.1과 합쳐 `sync-ui.*`는 **32개**이고 패키지 전체는 React 28·Vue 23·Svelte 21·Preact 20·Solid 20이다.

| 주입 | 결과 |

## 도구 메모

커넥터 테스트를 단일 파일로 반복 실행하면 vitest가 `close timed out after 10000ms` 뒤에도 종료하지 않는다. `hanging-process` 리포터로 확인한 결과 **열린 파일 핸들 105개, 타이머 0개**이고 스택은 모두 unknown이다. 커넥터 코드가 아니라 vite/plugin의 teardown 문제이며, 같은 패키지 안에서도 파일에 따라 갈린다(`test.test.ts`는 멈추고 `integration.test.ts`는 아니다). 전체 `pnpm gate`에서는 재현되지 않는다. 반복 실행이 필요하면 요약 줄이 로그에 나타난 뒤 프로세스를 죽이는 watchdog을 쓴다.
