# Phase 8.8 — 실제 브라우저 수행 장치

[Phase 8](./PHASE8.md) 8단계. 계획 일자 2026-09-26.

## 이 단계가 만드는 것과 만들지 않는 것

8.7은 사람이 브라우저에서 M2-01~20을 수행하는 단계다. 세 세션을 들여 **React 한 종에서 7개 항목**(통과 5, 부분 2)을 채웠고, Preact·Vue·Svelte·Solid는 브라우저 증거가 **0**이다. 8.7의 존재 이유가 "모델은 다섯 데모가 공유하니 화면이 갈리면 커넥터 탓"([DC8-5-01](./PHASE8_5.md))이라면 실제 행렬은 **20항목 × 5데모 = 100칸**이고, 지금까지 채운 것은 7칸이다. 같은 속도로는 끝나지 않는다.

이 단계는 그 수행을 **실제 브라우저에서 자동으로** 돌리는 장치를 만든다. Playwright가 띄우는 Chromium은 실제 브라우저이고 실제 DOM 이벤트로 커넥터 경로를 그대로 지나가므로, 그 실행은 8.7이 요구하는 것과 같은 종류의 증거다([DC8-08](./PHASE8.md)).

만들지 않는 것:

- **모델을 읽는 e2e 단언.** 그것은 `examples/shared`의 vitest를 브라우저에서 한 번 더 돌리는 것이고, 다섯 화면이 갈리는 지점을 건드리지 않는다.
- **jsdom 증거의 승격.** `check:examples`의 jsdom 실행과 Node 서버 렌더에 대한 [DC8-04](./PHASE8.md)의 금지는 그대로다.
- **사람 판단의 대체.** 레이아웃, 가독성("한 화면이 두 사실을 따로 말하는가"), DevTools만 보여 주는 신호는 계속 사람이 본다.
- **gate 편입.** 브라우저 내려받기와 예제 빌드가 필요하므로 19단계 gate에 넣지 않고 `pnpm test:e2e`로 분리한다.

## 요구와 결정

- [ ] **DC8-8-01 / 단언은 렌더된 DOM에서만 읽는다:** 커넥터가 모델을 화면으로 옮기는 그 구간이 8.7이 검증하려는 전부다. 판독기는 `page` 위에서 `data-field` 속성으로 값을 읽고, 모델이나 `window`에 노출된 어떤 객체도 읽지 않는다. 데모에 판독용 전역을 심지 않는다 — 심으면 그것을 읽는 유혹이 생기고, 그 순간 이 장치는 vitest의 재실행이 된다.
- [ ] **DC8-8-02 / 시나리오는 하나, 판독기는 둘:** 시나리오(`examples/shared/src/scenarios.ts`)는 누를 조작 `OperationId`와 기대 판독 `ScreenReading`만 담은 데이터다. **vitest는 그 시나리오를 `model.run`으로 눌러 `resourcePanel()`·`requestPanel()` 투영에서 판독하고, e2e는 같은 시나리오를 실제 버튼으로 눌러 DOM에서 판독한다.** 같은 기대값을 두 경로가 통과해야 하므로, 둘이 갈리면 결함이 모델 쪽인지 렌더 쪽인지 그 자리에서 좁혀진다. 기대값을 두 벌 관리하지 않는 것이 요점이다.
- [ ] **DC8-8-03 / 다섯 화면은 서로도 대조한다:** 시나리오마다 다섯 데모의 판독 수열을 모아 **서로 deep-equal인지** 먼저 본다. 다섯이 갈리면 커넥터 결함이고, 다섯이 일치하면서 기대값과 다르면 라이브러리·fixture 결함이거나 기대값이 틀린 것이다. 두 실패를 구별해 보고한다.
- [x] **DC8-8-04 / 선택자 계약은 공유 모듈이 정하고, e2e가 확인한다:** 버튼은 **이미 다섯 데모 전부가 `data-operation="<operationId>"`를 붙이고 있다**(`scripts/check-example-operations.mjs`가 그 속성의 존재를 소스에서 요구해 왔다) — 새 속성을 만들 필요가 없었다. 남은 것은 값 쪽이다: `data-field="<name>"`, 요청 표의 줄에 `data-request="<요청 ID>"`와 `data-cell="key|revision|outcome"`. 이름은 `examples/shared`가 내보내는 계약에서 오고 다섯 데모가 붙인다. **계약 준수는 소스 검사가 아니라 e2e로 확인한다** — 소스에 속성이 있다는 사실은 화면에 났다는 증거가 아니다([DC8-5-17](./PHASE8_5.md)). 판독은 개수만 세지 않고 **id 집합을 카탈로그와 대조**한다: 하나가 빠지고 하나가 중복되면 개수는 맞는다.
- [ ] **DC8-8-05 / 콘솔과 페이지 예외는 실패다:** `page.on('console')`의 error와 `page.on('pageerror')`를 수집해 하나라도 있으면 시나리오를 실패시키고 전문을 기록에 붙인다. Phase 8.2가 손으로 찾은 Svelte `subscriber_queue` 오염이 바로 이 부류이고, hydration 불일치 경고도 여기로 들어온다.
- [ ] **DC8-8-06 / 데모 빌드 설정은 건드리지 않는다:** 빌드된 `dist`를 각자의 포트에서 `vite preview`로 띄우고 Playwright의 `webServer` 배열에 다섯을 넣는다. 한 서버의 하위 경로로 모으려면 데모마다 `base`를 바꿔야 하고, 그것은 `check-example-bundles`가 보는 자산 경로까지 흔든다. 프로세스 다섯 개가 설정 변경보다 싸다.
- [ ] **DC8-8-07 / 장치의 검증력은 커넥터 결함 주입으로 확인한다:** 커넥터 **한 종에만** 결함을 주입해(구독 해제 누락·갱신 누락 등) 그 데모만 실패하고 나머지 넷은 통과하는 것을 본다. 이것이 DC8-5-01이 약속했지만 끝까지 증명된 적 없는 명제이고, 이 장치의 존재 이유다. 주입 뒤 원본과 `diff`로 대조해 복원한다.
- [ ] **DC8-8-08 / 칸에는 출처를 적는다:** 체크리스트의 결과란에 "e2e 실행으로 채움"과 구현 SHA·브라우저 버전·시나리오 이름·`pnpm test:e2e` 명령을 함께 남긴다. transcript는 gitignore 아래에 쓰고, 판정에 쓴 값은 지금까지의 기록처럼 문장으로 인용한다. **출처를 지운 통과는 남기지 않는다.**
- [ ] **DC8-8-09 / 사람이 볼 항목을 명시한다:** 항목군마다 한 종은 사람이 표본으로 확인하고, 자동이 볼 수 없는 것은 이름을 적어 남긴다. M2-04의 "불필요한 갱신"은 DevTools의 *Highlight updates* 대신 **데모에 컴포넌트별 렌더 카운터를 넣어** 기계 판정으로 바꾼다 — 눈으로 깜빡임을 세는 것보다 강한 증거다.

## 구현 단계와 기준 테스트

각 단계는 끝난 자리에서 멈출 수 있어야 한다.

1. **장치 뼈대 (완료).** 루트에 `@playwright/test`(chromium만), `examples/e2e` 워크스페이스에 `playwright.config.ts`와 다섯 `webServer`, 루트 스크립트 `pnpm test:e2e`(= `build:examples` + `playwright test`). **기준 테스트:** 다섯 데모가 모두 열리고 조작 버튼 45개가 보인다 — **통과**, 아래 검증 절.
2. **선택자 계약 (버튼 완료, 값 남음).** 버튼은 이미 `data-operation`이 있어 e2e 대조만 붙였다(DC8-8-04). 남은 것은 값 쪽 — `examples/shared`가 field 이름 계약을 내보내고 다섯 데모가 `data-field`·요청 줄 속성을 붙인다. **기준 테스트:** 다섯 데모에서 계약의 모든 field가 DOM에 있고, `data-operation`이 `OPERATION_IDS`와 정확히 일대일이다(빠짐도 여분도 없다).
3. **시나리오 자료형과 두 판독기.** `ScreenReading`과 시나리오 배열, 모델 판독기(vitest)와 DOM 판독기(e2e). 첫 시나리오는 **M2-11 항목 1·2·6**(계측이 방금 들어갔다 — [PHASE8_5 단계 14](./PHASE8_5.md)). **기준 테스트:** 같은 시나리오가 vitest의 모델 판독과 e2e의 DOM 판독에서 같은 기대값을 통과한다.
4. **다섯 화면 대조와 기록.** 시나리오당 다섯 판독 수열을 모아 deep-equal을 단언하고, 불일치는 어느 데모가 어느 단계에서 어떻게 달랐는지로 보고한다. 콘솔·페이지 예외 수집을 붙인다. **기준 테스트:** M2-11 시나리오가 다섯 종에서 일치하고 콘솔 오류가 0이다.
5. **검증력 확인(주입).** 커넥터 한 종에 결함 2종을 주입해 **그 종만** 실패하는 것을 확인하고, 계약 속성 하나를 지워 2단계 테스트가 실패하는 것을 확인한다. **기준 테스트:** 주입 3종 전부가 잡히고, 주입 뒤 `diff`로 복원이 확인된다.
6. **남은 항목 이식.** 체크리스트 항목을 시나리오로 옮긴다. 이미 React로 통과한 7개를 먼저 옮겨 **다섯 종으로 넓히고**(회귀 감시가 생긴다), 그다음 미수행 13개를 항목 순서대로 채운다. **기준 테스트:** 항목마다 다섯 종 일치 + 기대값 통과, 그리고 체크리스트 칸에 DC8-8-08의 출처가 적혀 있을 것.
7. **Test Hardening과 통합.** 시나리오가 실제로 판정하는지 항목별로 주입 1종씩 확인한다. SSR 데모(React 5191·Vue 5192)의 hydration과 `examples/bundles`의 UMD script 태그 로드를 시나리오로 넣는다. **기준 테스트:** hydration 경고가 콘솔 수집으로 잡히고, UMD 네 조합의 판정 행을 실제 브라우저에서 읽는다.

## 종료 기준

- 다섯 데모가 같은 시나리오 집합을 실제 브라우저에서 통과하고, 판독이 서로 일치한다.
- 커넥터 결함 주입이 그 데모에서만 실패한다(DC8-8-07).
- 체크리스트의 모든 e2e 칸에 출처가 적혀 있다(DC8-8-08).
- 사람이 볼 항목이 이름으로 남아 있고, 그중 표본이 수행돼 있다(DC8-8-09).
- `pnpm test:e2e`가 문서화된 명령 하나로 재현된다. 19단계 gate 결과는 불변이다.

## 위험과 주의

- **장치가 초록인 것이 화면이 옳다는 뜻은 아니다.** 19단계 gate가 매번 통과하는 동안 손으로 데모 결함 열넷(B8-7-01~14)이 나왔다. 자동화가 놓친 이유는 자동이라서가 아니라 화면을 보지 않았기 때문이고, 이 장치는 그 하나를 고치는 것일 뿐이다. 기대값이 틀리면 다섯 종이 다정하게 같이 틀린다 — **다섯 일치는 커넥터 증거이고 정확성 증거가 아니다.**
- **시나리오는 클릭 수열이 아니라 판정이다.** "버튼을 눌렀다"만 기록하면 [B8-7-05](./MANUAL_TEST_CHECKLIST.md#b8-7-05)(라벨이 동작과 달랐다)를 그대로 재현한다. 단계마다 무엇이 참이어야 하는지를 기대 판독으로 적는다.
- **정지 조건을 화면이 갱신하는 값으로 잡는다.** [B8-7-13](./MANUAL_TEST_CHECKLIST.md#b8-7-13)이 그 함정이었다. 재시도 한 번은 완료 두 번이고, 시나리오는 횟수를 세지 말고 조건이 만족될 때까지 돈다.
- 브라우저 내려받기(~수백 MB)와 예제 빌드가 선행 조건이다. CI에 넣을지는 이 단계의 결정이 아니다.
- Playwright의 `webServer` 다섯은 포트 충돌에 약하다. 데모의 dev 포트(5181~5186·5191·5192)와 겹치지 않는 대역을 쓴다.
- 판독기가 `toLocaleTimeString()` 같은 지역·시각 의존 값을 읽으면 기록이 매 실행 달라진다. 시간 열은 판독에서 제외하거나 존재 여부만 본다.

## 검증

### 단계 1~2 — 첫 실제 브라우저 실행 (2026-09-26)

`pnpm test:e2e`가 예제 5종을 빌드하고, 각자의 `dist`를 4181~4185에서 `vite preview`로 띄우고, Chromium(headless shell 153.0.8010.12)에서 다섯 페이지를 열어 조작 버튼 집합을 카탈로그와 대조한다. **5/5 통과, 콘솔 오류 0.** 이것이 **Preact·Vue·Svelte·Solid의 첫 브라우저 증거**다 — 이 문서 전까지 브라우저에서 확인된 데모는 React 한 종뿐이었다.

**검증력 확인 — 데모 한 종에만 결함을 주입해 그 종만 실패했다.** Solid 데모의 버튼 루프를 `group.operations.filter(([id]) => id !== 'refetch')`로 바꿔 버튼 하나를 빼자:

| 검사 | 결과 |
| --- | --- |
| `node scripts/check-example-operations.mjs` | **놓쳤다** — "다섯 데모가 모두 45개를 렌더한다"고 답했다 |
| `pnpm test:e2e` | **solid만 실패**, 나머지 넷 통과 |

소스 검사의 좁힘 탐지 정규식은 `OPERATION_GROUPS.filter|slice|find`를 보는데 주입은 `group.operations` 쪽이었다. **소스에 카탈로그를 렌더하는 코드가 있다는 것과 버튼이 화면에 났다는 것은 다른 명제이고**, 그 차이를 처음으로 실제로 잡았다. [DC8-5-01](./PHASE8_5.md)이 전제한 "화면이 갈리면 커넥터 탓"이 이제 탐지 가능하다. 주입 뒤 `diff`로 복원을 확인했다.

`pnpm gate` 19단계와 `pnpm check:examples`는 불변으로 통과한다 — `examples/e2e`의 스크립트 이름은 `test`가 아니라 `e2e`이므로 `pnpm -r test`(gate의 test 단계)가 브라우저를 열지 않는다. 새 워크스페이스는 `types:examples`의 타입 검사에는 포함된다.
