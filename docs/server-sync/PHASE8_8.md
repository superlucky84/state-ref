# Phase 8.8 — 실제 브라우저 수행 장치

[Phase 8](./PHASE8.md) 8단계. 계획 일자 2026-09-26.

## 이 단계가 만드는 것과 만들지 않는 것

8.7은 사람이 브라우저에서 M2-01~20을 수행하는 단계다. 세 세션을 들여 **React 한 종에서 7개 항목**(통과 5, 부분 2)을 채웠고, Preact·Vue·Svelte·Solid는 브라우저 증거가 **0**이다. 8.7의 존재 이유가 "모델은 다섯 데모가 공유하니 화면이 갈리면 커넥터 탓"([DC8-5-01](./PHASE8_5.md))이라면 실제 행렬은 **20항목 × 5데모 = 100칸**이고, 지금까지 채운 것은 7칸이다. 같은 속도로는 끝나지 않는다.

이 단계는 그 수행을 **실제 브라우저에서 자동으로** 돌리는 장치를 만든다. Playwright가 띄우는 Chromium은 실제 브라우저이고 실제 DOM 이벤트로 커넥터 경로를 그대로 지나가므로, 그 실행은 8.7이 요구하는 것과 같은 종류의 증거다([DC8-08](./PHASE8.md)).

만들지 않는 것:

- **모델을 읽는 e2e 단언.** 그것은 `examples/shared`의 vitest를 브라우저에서 한 번 더 돌리는 것이고, 다섯 화면이 갈리는 지점을 건드리지 않는다.
- **jsdom 증거의 승격.** `check:examples`의 jsdom 실행과 Node 서버 렌더에 대한 [DC8-04](./PHASE8.md)의 금지는 그대로다.
- **사람 판단의 대체.** 레이아웃, 가독성("한 화면이 두 사실을 따로 말하는가"), DevTools만 보여 주는 신호는 계속 사람이 본다.
- **gate 편입.** 브라우저 내려받기와 예제 빌드가 필요하므로 19단계 gate에 넣지 않고 `pnpm test:e2e`로 분리한다.

## 요구와 결정

- [ ] **DC8-8-01 / 단언은 렌더된 DOM에서만 읽는다:** 커넥터가 모델을 화면으로 옮기는 그 구간이 8.7이 검증하려는 전부다. 판독기는 `page` 위에서 `data-field` 속성으로 값을 읽고, 모델이나 `window`에 노출된 어떤 객체도 읽지 않는다. 데모에 판독용 전역을 심지 않는다 — 심으면 그것을 읽는 유혹이 생기고, 그 순간 이 장치는 vitest의 재실행이 된다.
- [ ] **DC8-8-02 / 시나리오는 하나, 판독기는 둘:** 시나리오(`examples/shared/src/scenarios.ts`)는 누를 조작 `OperationId`와 기대 판독 `ScreenReading`만 담은 데이터다. **vitest는 그 시나리오를 `model.run`으로 눌러 `resourcePanel()`·`requestPanel()` 투영에서 판독하고, e2e는 같은 시나리오를 실제 버튼으로 눌러 DOM에서 판독한다.** 같은 기대값을 두 경로가 통과해야 하므로, 둘이 갈리면 결함이 모델 쪽인지 렌더 쪽인지 그 자리에서 좁혀진다. 기대값을 두 벌 관리하지 않는 것이 요점이다.
- [ ] **DC8-8-03 / 다섯 화면은 서로도 대조한다:** 시나리오마다 다섯 데모의 판독 수열을 모아 **서로 deep-equal인지** 먼저 본다. 다섯이 갈리면 커넥터 결함이고, 다섯이 일치하면서 기대값과 다르면 라이브러리·fixture 결함이거나 기대값이 틀린 것이다. 두 실패를 구별해 보고한다.
- [x] **DC8-8-04 / 선택자 계약은 공유 모듈이 정하고, e2e가 확인한다:** 버튼은 **이미 다섯 데모 전부가 `data-operation="<operationId>"`를 붙이고 있다**(`scripts/check-example-operations.mjs`가 그 속성의 존재를 소스에서 요구해 왔다) — 새 속성을 만들 필요가 없었다. 남은 것은 값 쪽이다: `data-field="<name>"`, 요청 표의 줄에 `data-request="<요청 ID>"`와 `data-cell="key|revision|outcome"`. 이름은 `examples/shared`가 내보내는 계약에서 오고 다섯 데모가 붙인다. **계약 준수는 소스 검사가 아니라 e2e로 확인한다** — 소스에 속성이 있다는 사실은 화면에 났다는 증거가 아니다([DC8-5-17](./PHASE8_5.md)). 판독은 개수만 세지 않고 **id 집합을 카탈로그와 대조**한다: 하나가 빠지고 하나가 중복되면 개수는 맞는다.
- [ ] **DC8-8-05 / 콘솔과 페이지 예외는 실패다:** `page.on('console')`의 error와 `page.on('pageerror')`를 수집해 하나라도 있으면 시나리오를 실패시키고 전문을 기록에 붙인다. Phase 8.2가 손으로 찾은 Svelte `subscriber_queue` 오염이 바로 이 부류이고, hydration 불일치 경고도 여기로 들어온다.
- [ ] **DC8-8-06 / 데모 빌드 설정은 건드리지 않는다:** 빌드된 `dist`를 각자의 포트에서 `vite preview`로 띄우고 Playwright의 `webServer` 배열에 다섯을 넣는다. 한 서버의 하위 경로로 모으려면 데모마다 `base`를 바꿔야 하고, 그것은 `check-example-bundles`가 보는 자산 경로까지 흔든다. 프로세스 다섯 개가 설정 변경보다 싸다.
- [ ] **DC8-8-07 / 장치의 검증력은 커넥터 결함 주입으로 확인한다:** 커넥터 **한 종에만** 결함을 주입해(구독 해제 누락·갱신 누락 등) 그 데모만 실패하고 나머지 넷은 통과하는 것을 본다. 이것이 DC8-5-01이 약속했지만 끝까지 증명된 적 없는 명제이고, 이 장치의 존재 이유다. 주입 뒤 원본과 `diff`로 대조해 복원한다.
- [ ] **DC8-8-08 / 칸에는 출처를 적는다:** 체크리스트의 결과란에 "e2e 실행으로 채움"과 구현 SHA·브라우저 버전·시나리오 이름·`pnpm test:e2e` 명령을 함께 남긴다. transcript는 gitignore 아래에 쓰고, 판정에 쓴 값은 지금까지의 기록처럼 문장으로 인용한다. **출처를 지운 통과는 남기지 않는다.**
- [x] **DC8-8-10 / 판독은 정착된 화면에서 한다:** 다섯 프레임워크의 배치 방식이 다르다 — Vue는 자기 tick에 반영하므로, 두 번 누르고 한 번 읽으면 Vue 화면이 한 조작 뒤처진 것으로 **잘못** 보인다. 그것은 커넥터 결함이 아니고 결함으로 보고돼서도 안 된다. `readSettled`는 **두 번 연속 읽은 값이 같을 때** 정착으로 보며, 프레임워크별 지식을 전혀 쓰지 않는다. 판독 사이에 간격이 필요하다 — 한 프레임 안에서 두 번 읽으면 둘 다 같은 낡은 DOM을 보고 정착처럼 보인다(이 실수를 한 번 했다). 끝내 정착하지 않는 화면은 결함이므로 기다리지 않고 던진다. **정말로 진행 중인 것(떠 있는 요청·재시도 체인)은 시간이 아니라 조작으로 끝낸다.**
- [ ] **DC8-8-09 / 사람이 볼 항목을 명시한다:** 항목군마다 한 종은 사람이 표본으로 확인하고, 자동이 볼 수 없는 것은 이름을 적어 남긴다. M2-04의 "불필요한 갱신"은 DevTools의 *Highlight updates* 대신 **데모에 컴포넌트별 렌더 카운터를 넣어** 기계 판정으로 바꾼다 — 눈으로 깜빡임을 세는 것보다 강한 증거다.

## 구현 단계와 기준 테스트

각 단계는 끝난 자리에서 멈출 수 있어야 한다.

1. **장치 뼈대 (완료).** 루트에 `@playwright/test`(chromium만), `examples/e2e` 워크스페이스에 `playwright.config.ts`와 다섯 `webServer`, 루트 스크립트 `pnpm test:e2e`(= `build:examples` + `playwright test`). **기준 테스트:** 다섯 데모가 모두 열리고 조작 버튼 45개가 보인다 — **통과**, 아래 검증 절.
2. **선택자 계약 (완료).** 버튼은 이미 `data-operation`이 있어 e2e 대조만 붙였다. 값 쪽은 `examples/shared/src/fields.ts`가 카드 제목·field 라벨·카드별 field 목록을 내보내고, 다섯 데모가 `data-card`·`data-field`와 요청 줄의 `data-request`·`data-cell`을 붙인다(DC8-8-04). **기준 테스트:** 다섯 데모에서 계약의 모든 카드와 `always` field가 DOM에 있고, `data-operation`이 `OPERATION_IDS`와 정확히 일대일이다 — **통과**, 아래 검증 절.
3. **시나리오 자료형과 두 판독기 (완료).** `ScreenReading`(공유), 모델 판독기 `screenOf`(`examples/shared/src/screen.ts`), DOM 판독기 `readSettled`(`examples/e2e/src/read.ts`), 시나리오와 비교 의미를 담은 `scenarios.ts`. **기준 테스트:** 같은 시나리오가 모델 판독과 DOM 판독에서 같은 기대값을 통과한다 — **통과**, 아래 검증 절.
4. **다섯 화면 대조와 기록 (완료).** 초기 화면·로드 후 화면, 그리고 **시나리오의 단계마다** 다섯 판독이 deep-equal인지 단언하고 불일치를 단계 단위로 보고한다. 콘솔·페이지 예외 수집이 붙어 있다. **기준 테스트:** M2-11 시나리오가 다섯 종에서 일치하고 콘솔 오류가 0이다 — **통과.**
5. **검증력 확인(주입) (완료).** 커넥터 한 종에 결함 2종을 주입해 **그 종만** 실패하는 것을 확인했고, 기대값이 이름 붙이지 않은 필드를 한 데모에서만 바꿔 **일치 단언만** 걸리는 것도 확인했다. **기준 테스트:** 주입 전부가 잡히고 `diff`로 복원이 확인된다 — **통과**, 아래 검증 절.
6. **남은 항목 이식 (진행 중).** 체크리스트 항목을 시나리오로 옮긴다. 이미 React로 통과한 것을 먼저 옮겨 **다섯 종으로 넓히고**(회귀 감시가 생긴다), 그다음 미수행 12개를 항목 순서대로 채운다. **기준 테스트:** 항목마다 다섯 종 일치 + 기대값 통과, 그리고 체크리스트 칸에 DC8-8-08의 출처가 적혀 있을 것. **진행:** M2-11 항목 1·2·6(신규 통과), M2-10(이식 — 넷째는 `M2-11-6`이 겸함), M2-07·M2-05·M2-08·M2-09(이식). 시나리오 **16개**, `examples/shared` **68개**, 브라우저 스위트 **28개**, 조작 **46개**. **다섯 종 증거가 붙은 항목: M2-05·07·08·09·10·11.**
7. **Test Hardening과 통합.** 시나리오가 실제로 판정하는지 항목별로 주입 1종씩 확인한다. SSR 데모(React 5191·Vue 5192)의 hydration과 `examples/bundles`의 UMD script 태그 로드를 시나리오로 넣는다. **기준 테스트:** hydration 경고가 콘솔 수집으로 잡히고, UMD 네 조합의 판정 행을 실제 브라우저에서 읽는다.

## 종료 기준

- 다섯 데모가 같은 시나리오 집합을 실제 브라우저에서 통과하고, 판독이 서로 일치한다.
- 커넥터 결함 주입이 그 데모에서만 실패한다(DC8-8-07).
- 체크리스트의 모든 e2e 칸에 출처가 적혀 있다(DC8-8-08).
- 사람이 볼 항목이 이름으로 남아 있고, 그중 표본이 수행돼 있다(DC8-8-09).
- `pnpm test:e2e`가 문서화된 명령 하나로 재현된다. 19단계 gate 결과는 불변이다.

## 위험과 주의

- **장치가 초록인 것이 화면이 옳다는 뜻은 아니다.** 19단계 gate가 매번 통과하는 동안 손으로 데모 결함 열넷(B8-7-01~14)이 나왔다. 자동화가 놓친 이유는 자동이라서가 아니라 화면을 보지 않았기 때문이고, 이 장치는 그 하나를 고치는 것일 뿐이다. 기대값이 틀리면 다섯 종이 다정하게 같이 틀린다 — **다섯 일치는 커넥터 증거이고 정확성 증거가 아니다.**
- **시나리오는 클릭 수열이 아니라 판정이다.** "버튼을 눌렀다"만 기록하면 [B8-7-05](./MANUAL_TEST_CHECKLIST.md#b8-7-05)(라벨이 동작과 달랐다)를 그대로 재현한다. 단계마다 무엇이 참이어야 하는지를 기대 판독으로 적는다.
- **정지 조건을 화면이 갱신하는 값으로 잡는다.** [B8-7-13](./MANUAL_TEST_CHECKLIST.md#b8-7-13)이 그 함정이었다. 재시도 한 번은 완료 두 번이고, 시나리오는 횟수를 세지 말고 조건이 만족될 때까지 돈다.
- 브라우저 내려받기(~수백 MB)와 예제 빌드가 선행 조건이다. CI에 넣을지는 이 단계의 결정이 아니다.
- Playwright의 `webServer` 다섯은 포트 충돌에 약하다. 데모의 dev 포트(5181~5186·5191·5192)와 겹치지 않는 대역을 쓴다.
- 판독기가 `toLocaleTimeString()` 같은 지역·시각 의존 값을 읽으면 기록이 매 실행 달라진다. 시간 열은 판독에서 제외하거나 존재 여부만 본다.

## 검증

### 단계 1 — 첫 실제 브라우저 실행 (2026-09-26)

`pnpm test:e2e`가 예제 5종을 빌드하고, 각자의 `dist`를 4181~4185에서 `vite preview`로 띄우고, Chromium(headless shell 153.0.8010.12)에서 다섯 페이지를 열어 조작 버튼 집합을 카탈로그와 대조한다. **5/5 통과, 콘솔 오류 0.** 이것이 **Preact·Vue·Svelte·Solid의 첫 브라우저 증거**다 — 이 문서 전까지 브라우저에서 확인된 데모는 React 한 종뿐이었다.

**검증력 확인 — 데모 한 종에만 결함을 주입해 그 종만 실패했다.** Solid 데모의 버튼 루프를 `group.operations.filter(([id]) => id !== 'refetch')`로 바꿔 버튼 하나를 빼자:

| 검사 | 결과 |
| --- | --- |
| `node scripts/check-example-operations.mjs` | **놓쳤다** — "다섯 데모가 모두 45개를 렌더한다"고 답했다 |
| `pnpm test:e2e` | **solid만 실패**, 나머지 넷 통과 |

소스 검사의 좁힘 탐지 정규식은 `OPERATION_GROUPS.filter|slice|find`를 보는데 주입은 `group.operations` 쪽이었다. **소스에 카탈로그를 렌더하는 코드가 있다는 것과 버튼이 화면에 났다는 것은 다른 명제이고**, 그 차이를 처음으로 실제로 잡았다. [DC8-5-01](./PHASE8_5.md)이 전제한 "화면이 갈리면 커넥터 탓"이 이제 탐지 가능하다. 주입 뒤 `diff`로 복원을 확인했다.

`pnpm gate` 19단계와 `pnpm check:examples`는 불변으로 통과한다 — `examples/e2e`의 스크립트 이름은 `test`가 아니라 `e2e`이므로 `pnpm -r test`(gate의 test 단계)가 브라우저를 열지 않는다. 새 워크스페이스는 `types:examples`의 타입 검사에는 포함된다.

### 단계 2 — 값 쪽 계약 (2026-09-26)

라벨과 카드 제목이 다섯 데모에 **각자 리터럴로 중복**돼 있었다. 실측해 보니 28개 라벨이 다섯 곳에서 정확히 일치했지만, 그것을 지키는 장치는 없었다. `examples/shared/src/fields.ts`가 `CARD_TITLE`·`FIELD_LABEL`·`CARD_FIELDS`를 갖고, 데모는 `label(field)`를 렌더하며 행에 `data-field`를 붙인다. 리터럴 라벨은 다섯 데모 전부에서 0개가 되었다.

같은 라벨이 resource 패널과 draft에 모두 나오므로(`도시`·`우편번호`·`version / conflicts`) 판독 범위는 페이지가 아니라 **카드**다 — `[data-card="resource-a"] [data-field="status"]`. `draftDirty`만 별도 id인데, 화면이 resource에는 `dirty (로컬 차이)`, draft에는 `dirty`라고 적기 때문이다. 표를 깔끔하게 만들자고 사람이 읽는 글자를 바꾸지는 않는다.

Vue·Svelte는 인라인 `div.row`를 쓰고 있어 `Row`/`Flag` 컴포넌트를 새로 만들었다(React·Preact·Solid에는 이미 있었다). 값이 편집 가능한 `도시` 행은 기본 슬롯을 바꿔 끼운다. 카드별 필수 field는 `always`와 `onceLoaded`로 갈라 둔다 — 로드 전에 값 행을 요구하는 검사는 데모에게 **없는 기준을 보여 달라고** 요구하는 것이고, 그것이 M2-04가 금지하는 바로 그 화면이다.

**이번에도 한 종만 실패했고, 이번 것은 주입이 아니라 실제 누락이었다.** Solid의 `Row`·`Flag`에 `data-field`를 붙이는 것을 빠뜨렸는데, 다른 넷이 통과하는 동안 solid만 실패했다. 타입 검사도 빌드도 소스 검사도 통과한 상태였다 — 속성이 없어도 컴파일에는 아무 문제가 없다. 이어서 Vue의 `data-card="requests"`를 지우는 주입 1종으로 카드 범위도 확인했고, vue만 실패했다. 복원은 `diff`로 대조했다.

| 확인 | 결과 |
| --- | --- |
| 다섯 데모 × 계약 2종 | **10/10 통과**, 콘솔 오류 0 |
| Solid의 `data-field` 누락(실제) | solid만 실패 |
| Vue의 `data-card` 제거(주입) | vue만 실패 |
| `pnpm gate` 19단계 / `check:examples` | 불변 통과(다섯 데모 45개 렌더) |

### 단계 3~4 — DOM 판독기와 다섯 화면 대조 (2026-09-26)

`read.ts`의 `readScreen(page)`가 카드별 `data-field` 행과 요청 표의 안정적인 세 칸을 읽어 `ScreenReading`을 만든다. 모델도 `window` 전역도 읽지 않는다(DC8-8-01). 없는 카드는 빈 값이 아니라 **없는 것으로** 둔다 — draft 카드는 분기 전에는 존재하지 않고, 그것을 빈 카드로 읽으면 데모 간 차이가 묻힌다. 계약에 없는 field가 화면에 있으면 던진다.

그 판독기로 **초기 화면의 다섯 데모가 완전히 일치하는 것을 확인했다** — 31개 행과 요청 표 전체가 문자 단위로 같다. 이 프로젝트에서 DC8-5-01의 전제가 단언된 것은 이번이 처음이다. 부수 효과로, 라벨을 공유 표로 옮긴 이번 리팩터가 **화면 글자를 바꾸지 않았다**는 것도 같은 판독으로 확인됐다.

**검증력:** Svelte의 `고정한 제출` 자리 표시자만 `(없음)` → `(none)`으로 바꾸자 대조 테스트가 `svelte differs from react`와 함께 그 한 칸을 지목하며 실패했다. 복원은 `diff`로 대조했다.

**일치는 정확성이 아니다.** 다섯이 같이 틀릴 수 있고, 그것을 잡는 것은 시나리오의 기대값이다(DC8-8-03). 이 테스트가 좁히는 것은 "어디서 갈렸는가"이지 "무엇이 옳은가"가 아니다.

### 단계 3~4 (이어서) — 첫 대조가 찾은 결함 둘 (2026-09-26)

로드 **후** 화면까지 대조 범위를 넓히자 곧바로 둘이 나왔다. 값 행은 기준이 있어야 존재하므로 초기 화면 대조로는 닿을 수 없는 자리였다.

**[B8-7-15](./MANUAL_TEST_CHECKLIST.md#b8-7-15) — 같은 객체가 세 가지로 그려졌다.** `사무실` 값은 객체이고, 템플릿의 기본 문자열화는 프레임워크마다 다르다 — React·Preact·Solid `JSON.stringify`, Vue 들여쓴 JSON, **Svelte `String()` → `[object Object]`**. Svelte 화면은 그 값을 보여주지 못했고 그 행은 M2-15가 읽어야 하는 행이다. 다섯 데모가 모두 타입 검사·빌드·소스 검사를 통과하고 각자 잘 렌더하고 있었다. 문자열화를 공유 계약의 `show()`로 옮겼다 — **다섯이 같은 글자를 그려야 비교가 성립한다**는 것이 이 계약의 존재 이유다.

**CI-29 (라이브러리) — Vue 커넥터가 한 턴의 두 번째 쓰기를 버렸다.** `작업과 정책` 카드가 Vue에서만 항상 **이전 조작**을 보여줬다. 데모의 `bump()`는 tick·조작명·결과 셋을 한 턴에 쓰는데, `connectVue`의 에코 방지 가드가 **인바운드 갱신에서** 올라가고 microtask에서야 풀려 두 번째 이후 쓰기가 막혔다. 추적 기록:

| 누른 조작 | react·preact·svelte·solid | vue |
| --- | --- | --- |
| (시작) | `(없음)` | `(없음)` |
| `load` | `load` | `(없음)` |
| `가능한 요청 모두 완료` | `settle-all` | `load` |
| `focus 사건` | `focus` | `settle-all` |

**출시된 3.3.0에 있고**, 커넥터 스위트 35개·코어 338개·`examples/shared` 52개·`pnpm gate` 19단계가 전부 통과하는 동안 화면은 뒤처져 있었다 — 커넥터 테스트가 **한 턴에 잎 하나만** 쓰고 있었기 때문이다. 브라우저에서 찾은 뒤 커넥터 스위트에 반례(`PairWrite.vue`)를 먼저 써서 격리하고 고쳤다(Vue 35 → **36개**). 전체 기록은 [core-improvement의 CI-29](../core-improvement/REQUIREMENTS.md).

**첫 수정 시도는 틀렸다.** 가드를 아예 없애자 Vue 화면이 `pending / fetching`에 멈췄다 — `reactive`가 템플릿에 값의 **프록시**를 주므로 write-back의 동등성 검사가 자기 값을 알아보지 못하고 스토어에 clone을 덮어썼다. 가드는 필요하고, 틀린 것은 인바운드가 그것을 올린다는 점이었다. **증상이 사라졌다고 원인을 맞힌 것은 아니다.**

**이 두 건이 이 단계의 존재 이유를 증명한다.** 하나는 데모 결함이고 하나는 라이브러리 결함인데, 둘 다 자동 검사 전부가 초록인 상태로 화면에 올라가 있었다. 자동화가 놓친 이유는 자동이라서가 아니라 **화면을 서로 대조한 적이 없기 때문**이다.

### 단계 3~4 (완료) — 시나리오 하나, 판독기 둘 (2026-09-26)

시나리오는 **누를 조작과 그 뒤에 참이어야 하는 것**만 담은 데이터다. 기다리는 시간도, 재시도가 완료 몇 번인지도 담지 않는다 — 두 러너가 각자 **조건이 만족될 때까지 재시도**한다. 기대값은 부분이고 `{ contains }`를 지원한다. 단계마다 화면 전체를 적으면 무관한 행이 바뀔 때마다 깨지고, 그 단계가 말하려는 한 칸이 묻힌다.

비교 의미(`mismatches()`)는 한 함수다. 브라우저에서는 맞고 vitest에서는 미묘하게 다른 비교가 되면 안 된다. `POLICY_TEXT`도 공유 계약으로 옮겼다 — 모델 판독기가 화면과 **구분자까지 같은 글자**를 만들어야 기대값이 양쪽에서 같은 뜻을 갖는다.

M2-11의 도달 가능한 세 항목을 시나리오로 옮겨 **다섯 데모 전부에서 통과했고, 단계마다 다섯 판독이 일치했다.** 결과는 [체크리스트 M2-11](./MANUAL_TEST_CHECKLIST.md#m2-11)에 `e2e 실행으로 채움`으로 기록했다 — **이 문서의 장치가 채운 첫 체크리스트 칸이고, React 외의 데모에 증거가 붙은 첫 항목이다.**

| | 모델(vitest) | 브라우저(다섯 데모) |
| --- | --- | --- |
| `M2-11-1` 중단 | 통과 | 통과·일치 |
| `M2-11-2` 늦은 결과 폐기 | 통과 | 통과·일치 |
| `M2-11-6` 장벽 밖 조회 | 통과 | 통과·일치 |

**검증력 — 두 러너가 같은 결함을 잡고, 그 모양이 원인을 말한다.** fixture에서 DC8-5-49를 되돌려(예약이 abort 청취를 건너뛰지 않게) 돌리자 vitest의 `M2-11-2` 8단계가 실패하고, 브라우저에서도 **다섯 데모가 모두** 같은 8·12단계에서 실패했다. **다섯이 함께 실패하는 것은 커넥터가 아니라 fixture·라이브러리가 틀렸다는 신호다**(DC8-8-03) — 한 종만 실패하는 앞선 세 사례와 구별된다. 실패 메시지는 단계 번호와 그 단계를 둔 이유(`note`)를 함께 말한다.

### 단계 5 — 주입으로 확인한 두 가지 (2026-09-26)

**격리:** `connect-svelte`에 결함 2종을 주입했다. 둘 다 **svelte만** 실패하고 나머지 넷은 전 단계를 통과했으며, 실패 메시지가 단계 번호와 그 단계를 둔 이유를 함께 말한다.

| 주입 | 커넥터 자체 스위트 | 이 장치 |
| --- | --- | --- |
| 알림을 한 번씩 건너뛴다 | **잡았다** (6건 실패) | svelte만 실패 |
| 원시값 잎만 push한다(객체 선택은 갱신 안 됨) | **잡았다** (2건 실패) | svelte만 실패, 세 시나리오 전부에서 단계 지목 |
| solid만 `memo`에 접미사를 붙인다(기대값이 이름 붙이지 않은 필드) | 해당 없음 — 데모 쪽 주입 | **일치 단언만** 실패: `solid differs from react at step 3`, 값까지 지목 |

**심어 넣은 커넥터 결함은 두 번 모두 커넥터 스위트가 먼저 잡았다.** 그것은 이 장치의 실패가 아니라 스위트에 대한 좋은 소식이다 — 그리고 [CI-29](../core-improvement/REQUIREMENTS.md)가 왜 스위트를 통과했는지도 정확히 말해 준다. CI-29는 아무 데나 있는 결함이 아니라 **Vue 스위트의 특정 빈칸**(한 턴에 잎 여러 개를 쓰는 축)에 있었다. 이 장치는 유일한 그물이 아니라 **두 번째 그물**이고, 그 위에 다른 그물이 못 하는 두 가지를 한다: **한 화면으로 범위를 좁히는 것**과 **아무 기대값도 이름 붙이지 않은 차이를 잡는 것**.

**두 단언은 독립이다.** 세 번째 주입에서 기대값은 다섯 종 모두 통과했고 일치 단언만 실패했다. 뒤집으면, fixture를 되돌린 앞선 주입에서는 다섯이 **함께** 기대값을 실패했고 일치는 유지됐다. 그래서 실패의 모양이 그대로 원인의 위치를 말한다.

| 실패 모양 | 어디를 보아야 하는가 |
| --- | --- |
| 한 종만 기대값 실패 | 그 커넥터 |
| 다섯이 함께 기대값 실패, 일치 유지 | fixture 또는 라이브러리 (또는 기대값이 틀렸다) |
| 기대값은 전부 통과, 일치만 실패 | 어떤 기대값도 보지 않는 자리의 화면 차이 |

주입 3종 모두 원본과 `diff`로 대조해 복원했다.
