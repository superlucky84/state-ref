# Phase 8.8 — 실제 브라우저 수행 장치

[Phase 8](./PHASE8.md) 8단계. 계획 일자 2026-09-26.

## 이 단계가 만드는 것과 만들지 않는 것

8.7은 사람이 브라우저에서 M2-01~20을 수행하는 단계다. 세 세션을 들여 **React 한 종에서 7개 항목**(통과 5, 부분 2)을 채웠고, Preact·Vue·Svelte·Solid는 브라우저 증거가 **0**이다. 8.7의 존재 이유가 "모델은 다섯 데모가 공유하니 화면이 갈리면 커넥터 탓"([DC8-5-01](./PHASE8_5.md))이라면 실제 행렬은 **20항목 × 5데모 = 100칸**이고, 지금까지 채운 것은 7칸이다. 같은 속도로는 끝나지 않는다.

이 단계는 그 수행을 **실제 브라우저에서 자동으로** 돌리는 장치를 만든다. Playwright가 띄우는 Chromium은 실제 브라우저이고 실제 DOM 이벤트로 커넥터 경로를 그대로 지나가므로, 그 실행은 8.7이 요구하는 것과 같은 종류의 증거다([DC8-08](./PHASE8.md)).

만들지 않는 것:

- **모델을 읽는 e2e 단언.** 그것은 `examples/shared`의 vitest를 브라우저에서 한 번 더 돌리는 것이고, 다섯 화면이 갈리는 지점을 건드리지 않는다.
- **jsdom 증거의 승격.** `check:examples`의 jsdom 실행과 Node 서버 렌더에 대한 [DC8-04](./PHASE8.md)의 금지는 그대로다.
- **사람 판단의 대체.** 레이아웃, 가독성("한 화면이 두 사실을 따로 말하는가"), DevTools만 보여 주는 신호는 계속 사람이 본다.
- **gate 편입.** 브라우저 내려받기와 예제 빌드가 필요하므로 19단계 gate에 넣지 않고 `pnpm test:e2e`로 분리한다.

## 요구와 결정

- [ ] **DC8-8-01 / 단언은 렌더된 DOM에서만 읽는다:** 커넥터가 모델을 화면으로 옮기는 그 구간이 8.7이 검증하려는 전부다. 판독기는 `page` 위에서 `data-field` 속성으로 값을 읽고, 모델이나 `window`에 노출된 어떤 객체도 읽지 않는다. 데모에 판독용 전역을 심지 않는다 — 심으면 그것을 읽는 유혹이 생기고, 그 순간 이 장치는 vitest의 재실행이 된다.
- [ ] **DC8-8-02 / 시나리오는 하나, 판독기는 둘:** 시나리오(`examples/shared/src/scenarios.ts`)는 누를 조작 `OperationId`와 기대 판독 `ScreenReading`만 담은 데이터다. **vitest는 그 시나리오를 `model.run`으로 눌러 `resourcePanel()`·`requestPanel()` 투영에서 판독하고, e2e는 같은 시나리오를 실제 버튼으로 눌러 DOM에서 판독한다.** 같은 기대값을 두 경로가 통과해야 하므로, 둘이 갈리면 결함이 모델 쪽인지 렌더 쪽인지 그 자리에서 좁혀진다. 기대값을 두 벌 관리하지 않는 것이 요점이다.
- [ ] **DC8-8-03 / 다섯 화면은 서로도 대조한다:** 시나리오마다 다섯 데모의 판독 수열을 모아 **서로 deep-equal인지** 먼저 본다. 다섯이 갈리면 커넥터 결함이고, 다섯이 일치하면서 기대값과 다르면 라이브러리·fixture 결함이거나 기대값이 틀린 것이다. 두 실패를 구별해 보고한다.
- [x] **DC8-8-04 / 선택자 계약은 공유 모듈이 정하고, e2e가 확인한다:** 버튼은 **이미 다섯 데모 전부가 `data-operation="<operationId>"`를 붙이고 있다**(`scripts/check-example-operations.mjs`가 그 속성의 존재를 소스에서 요구해 왔다) — 새 속성을 만들 필요가 없었다. 남은 것은 값 쪽이다: `data-field="<name>"`, 요청 표의 줄에 `data-request="<요청 ID>"`와 `data-cell="key|revision|outcome"`. 이름은 `examples/shared`가 내보내는 계약에서 오고 다섯 데모가 붙인다. **계약 준수는 소스 검사가 아니라 e2e로 확인한다** — 소스에 속성이 있다는 사실은 화면에 났다는 증거가 아니다([DC8-5-17](./PHASE8_5.md)). 판독은 개수만 세지 않고 **id 집합을 카탈로그와 대조**한다: 하나가 빠지고 하나가 중복되면 개수는 맞는다.
- [ ] **DC8-8-05 / 콘솔과 페이지 예외는 실패다:** `page.on('console')`의 error와 `page.on('pageerror')`를 수집해 하나라도 있으면 시나리오를 실패시키고 전문을 기록에 붙인다. Phase 8.2가 손으로 찾은 Svelte `subscriber_queue` 오염이 바로 이 부류이고, hydration 불일치 경고도 여기로 들어온다.
- [ ] **DC8-8-06 / 데모 빌드 설정은 건드리지 않는다:** 빌드된 `dist`를 각자의 포트에서 `vite preview`로 띄우고 Playwright의 `webServer` 배열에 다섯을 넣는다. 한 서버의 하위 경로로 모으려면 데모마다 `base`를 바꿔야 하고, 그것은 `check-example-bundles`가 보는 자산 경로까지 흔든다. 프로세스 다섯 개가 설정 변경보다 싸다.
- [ ] **DC8-8-07 / 장치의 검증력은 커넥터 결함 주입으로 확인한다:** 커넥터 **한 종에만** 결함을 주입해(구독 해제 누락·갱신 누락 등) 그 데모만 실패하고 나머지 넷은 통과하는 것을 본다. 이것이 DC8-5-01이 약속했지만 끝까지 증명된 적 없는 명제이고, 이 장치의 존재 이유다. 주입 뒤 원본과 `diff`로 대조해 복원한다.
- [ ] **DC8-8-08 / 칸에는 출처를 적는다:** 체크리스트의 결과란에 "e2e 실행으로 채움"과 구현 SHA·브라우저 버전·시나리오 이름·`pnpm test:e2e` 명령을 함께 남긴다. transcript는 gitignore 아래에 쓰고, 판정에 쓴 값은 지금까지의 기록처럼 문장으로 인용한다. **출처를 지운 통과는 남기지 않는다.**
- [x] **DC8-8-10 / 판독은 정착된 화면에서 한다:** 다섯 프레임워크의 배치 방식이 다르다 — Vue는 자기 tick에 반영하므로, 두 번 누르고 한 번 읽으면 Vue 화면이 한 조작 뒤처진 것으로 **잘못** 보인다. 그것은 커넥터 결함이 아니고 결함으로 보고돼서도 안 된다. `readSettled`는 **두 번 연속 읽은 값이 같을 때** 정착으로 보며, 프레임워크별 지식을 전혀 쓰지 않는다. 판독 사이에 간격이 필요하다 — 한 프레임 안에서 두 번 읽으면 둘 다 같은 낡은 DOM을 보고 정착처럼 보인다(이 실수를 한 번 했다). 끝내 정착하지 않는 화면은 결함이므로 기다리지 않고 던진다. **정말로 진행 중인 것(떠 있는 요청·재시도 체인)은 시간이 아니라 조작으로 끝낸다.**
- [ ] **DC8-8-09 / 사람이 볼 항목을 명시한다:** 항목군마다 한 종은 사람이 표본으로 확인하고, 자동이 볼 수 없는 것은 이름을 적어 남긴다. M2-04의 "불필요한 갱신"은 DevTools의 *Highlight updates* 대신 **데모에 컴포넌트별 렌더 카운터를 넣어** 기계 판정으로 바꾼다 — 눈으로 깜빡임을 세는 것보다 강한 증거다.
- [ ] **DC8-8-11 / 관측 카드는 라이브러리의 공개 관측 표면만 읽는다:** `client.inspectCache()`·`inspectMutations()`·`subscribeCache()`·`subscribeMutations()`, 그리고 **데모가 소유한** 환경의 listener 수. 내부 구조에 손을 넣지 않는다. [M2-19](./MANUAL_TEST_CHECKLIST.md#m2-19)의 7·13항이 판정 대상으로 지목하는 것이 바로 그 공개 표면이고, 내부를 읽어 채운 칸은 그 항목이 요구한 것을 확인한 것이 아니다.
- [ ] **DC8-8-12 / 관측값은 tick으로 다시 그린다:** `inspectCache()`는 스냅숏이고 반응형이 아니다. 요청 카드의 선례대로 카드가 `ui.tick`을 구독하고, 모델이 캐시·WRITE 이벤트를 받을 때마다 tick을 올린다(이벤트 전달은 다음 turn으로 밀리므로 조작만으로는 늦는다). **비반응형 출처를 카드에 올린 실수가 이 프로젝트에 세 번 있었다** — [B8-7-13](./MANUAL_TEST_CHECKLIST.md#b8-7-13), [B8-7-18](./MANUAL_TEST_CHECKLIST.md#b8-7-18), 그리고 단계 6에서 내가 쓰고 지운 `조회 핸들` 행.
- [ ] **DC8-8-13 / 이벤트 누적 수를 기대값에 고정하지 않는다:** 캐시 이벤트 총수는 조작 수와 서버 알림 수에 따라 달라지는 값이고 `ui.tick` 파생값과 같은 함정이다(`메모 N`·`zip 9NN`). 화면이 보여 주는 것은 **마지막 (재)구독 이후**의 수이고, 시나리오는 그 값이 결정적인 자리에서만 고정한다 — 해제 직후의 `0`이 그 자리다.
- [ ] **DC8-8-14 / 이벤트의 필드 목록을 행으로 인쇄한다:** M2-19의 7·13항은 "query payload와 mutation DTO가 이벤트에 없어야 한다"를 요구한다. 불리언 한 칸보다 **관측된 키의 합집합을 그대로 인쇄**하는 것이 증거다 — payload가 새면 그 문자열이 바뀐다. 측정값(2026-09-27): 캐시 `kind,owners,queryKey,status`, WRITE `attempt,idempotent,linkedKeys,operationId,phase,scope,settledAt,startedAt`. `idempotent`은 불리언이고 키 값 자체는 없다.
- [ ] **DC8-8-15 / `owners 0`과 "캐시에서 사라짐"은 다른 사실이다:** 측정 결과 `key를 live/b로 전환` 뒤 `live/a`는 **owners 0으로 캐시에 남는다**(`size()`는 줄지 않는다). [M2-11](./MANUAL_TEST_CHECKLIST.md#m2-11) 다섯째 항목이 요구하는 "구독이 남지 않는다"는 그 owners 0으로 성립하고, 항목이 캐시 항목의 소멸까지 요구하는 것은 아니다. **`표시 해제`의 결과 문구는 이미 "구독도 남지 않는다"고 주장하고 있었고, 그것을 확인할 계측이 화면에 없었다.**
- [ ] **DC8-8-16 / WRITE 표에 시각 열을 두지 않는다:** `startedAt`·`settledAt`은 벽시계다. 요청 표에서와 같은 이유로 판독에서 제외한다 — 넣으면 기록이 실행마다 달라진다.
- [x] **DC8-8-17 / 다시 그리는 구독과 관측하는 구독을 분리한다:** 처음에는 하나로 묶어, 카드를 다시 그리는 일을 **시험 대상인 그 핸들**이 겸하게 했다. 결과는 `관측 구독 해제`를 누른 순간 캐시 표가 얼어붙는 것이었고 — 장치가 **다섯 데모 전부에서** 그것을 잡았다(`cache[0]/status: expected success / idle, got success / fetching`). 다섯이 함께 실패하는 모양은 커넥터가 아니라 fixture나 기대값이 틀렸다는 뜻이고, 이번에는 fixture였다. 그래서 두 쌍을 둔다: **다시 그리는 쌍**은 모델의 수명 동안 살아 있고 tick만 올리며, **관측하는 쌍**은 해제 조작이 놓고 카드가 세는 쪽이다. 뜻밖의 이득이 더 크다 — 이제 `구독 이후 이벤트 0`은 "이벤트가 흐르지 않았다"가 아니라 **"해제한 그 listener에게 오지 않았다"**는 주장이 된다(같은 흐름의 다른 listener는 표를 계속 갱신하고 있으므로). M2-19가 요구하는 것이 바로 그 listener 단위의 해제다.
- [ ] **DC8-8-18 / 둘째 client는 같은 key를 쓴다:** 다른 key라면 섞이지 않는 것이 당연하고 아무것도 주장하지 못한다. `profile`을 그대로 써야 "같은 key인데 기준·편집·요청이 공유되지 않는다"([M2-03](./MANUAL_TEST_CHECKLIST.md#m2-03) 여섯째 항목, R2-07)가 판정된다. 같은 key라서 두 캐시 표가 같은 이름의 줄을 들고 나란히 서는 것이 곧 증거다.
- [ ] **DC8-8-19 / 둘째 client 카드는 tick으로 읽는다:** 동적으로 생긴 조회 핸들마다 커넥터 훅을 만들면 다섯 데모에 `DraftCard` 같은 컴포넌트가 하나씩 더 늘어난다. 그 경로(`connectX(query.watchStatus)`)는 **패널 두 장이 이미 충분히 덮고 있고**, 이 카드의 목적은 커넥터가 아니라 **client 격리**다. 그래서 카드는 모델이 만든 문자열 묶음을 tick 구독으로 읽는다 — 관측 카드와 같은 방식이다. 대신 **probe client의 캐시 이벤트에도 repaint 구독을 걸어야** tick이 제때 오른다([DC8-8-17](#요구와-결정)과 같은 이유이며, 빠뜨리면 같은 종류의 실패가 다시 난다). 이 카드가 시험하지 않는 것을 적어 두는 것이 요점이다.
- [ ] **DC8-8-20 / 표는 카드 범위로 읽는다:** 두 client의 캐시 항목을 한 표에 섞으면 "client별"이 흐려진다. `cache`와 `mutations` 판독을 `changes`처럼 **카드별 목록**으로 바꾸고, 각 카드가 자기 `[data-cache]`만 들게 한다. 판독기는 이미 카드 범위로 `[data-change]`를 읽고 있었으므로 같은 자리에 붙는다.
- [x] **DC8-8-21 / 번들 페이지의 계약은 그 페이지들이 스스로 든다:** 다섯 데모의 라벨을 `fields.ts`로 모은 이유는 **한 화면을 다섯 벌 그리기** 때문이었다. 번들 페이지는 조합마다 한 장뿐이라 어긋날 상대가 없으므로 기대값은 `examples/e2e` 쪽에 둔다. `examples/bundles`가 지는 의무는 **행과 버튼의 안정된 id**(`data-row`·`data-action`)뿐이다 — 그리고 그것이 꼭 필요하다: 지금까지 판독은 `<dt>`의 한글 텍스트로 행을 찾고 있었고([DC8-8-04](#요구와-결정)가 피하려던 바로 그 모양), 라벨 한 단어를 고치면 장치가 깨진다. **반대로 `stateref-example-shared`를 가져오는 것은 금지다** — core 단독 페이지의 모듈 그래프에 `state-ref`와 `@stateref/sync`가 들어와 그 페이지가 증명하려는 경계를 스스로 무너뜨린다.
- [x] **DC8-8-22 / 번들 페이지는 한 origin에서 낸다:** ESM 조합 네 개는 각자 다른 디렉터리로 빌드되고 UMD는 다섯째이며, 모든 페이지가 자산을 `/assets/...`·`/vendor/...`로 **루트에서** 참조한다. 한 디렉터리로 모으려면 번들 빌드를 고쳐야 하고 그것은 [DC8-8-06](#요구와-결정)이 금지한다(자산 경로는 `check-example-bundles.mjs`가 읽는다). 그래서 작은 정적 서버 하나가 **다섯 루트를 순서대로** 뒤진다. 모호함은 **요청 시점에** 거절한다 — 두 루트가 같은 경로를 다른 내용으로 내면 500이다. 빌드 시점에 전수 검사하면 어떤 페이지도 요청하지 않는 파일까지 걸리고(ESM 루트마다 자기 `module-graph.json`이 있다) 그 예외 목록은 썩는다.

## 구현 단계와 기준 테스트

각 단계는 끝난 자리에서 멈출 수 있어야 한다.

1. **장치 뼈대 (완료).** 루트에 `@playwright/test`(chromium만), `examples/e2e` 워크스페이스에 `playwright.config.ts`와 다섯 `webServer`, 루트 스크립트 `pnpm test:e2e`(= `build:examples` + `playwright test`). **기준 테스트:** 다섯 데모가 모두 열리고 조작 버튼 45개가 보인다 — **통과**, 아래 검증 절.
2. **선택자 계약 (완료).** 버튼은 이미 `data-operation`이 있어 e2e 대조만 붙였다. 값 쪽은 `examples/shared/src/fields.ts`가 카드 제목·field 라벨·카드별 field 목록을 내보내고, 다섯 데모가 `data-card`·`data-field`와 요청 줄의 `data-request`·`data-cell`을 붙인다(DC8-8-04). **기준 테스트:** 다섯 데모에서 계약의 모든 카드와 `always` field가 DOM에 있고, `data-operation`이 `OPERATION_IDS`와 정확히 일대일이다 — **통과**, 아래 검증 절.
3. **시나리오 자료형과 두 판독기 (완료).** `ScreenReading`(공유), 모델 판독기 `screenOf`(`examples/shared/src/screen.ts`), DOM 판독기 `readSettled`(`examples/e2e/src/read.ts`), 시나리오와 비교 의미를 담은 `scenarios.ts`. **기준 테스트:** 같은 시나리오가 모델 판독과 DOM 판독에서 같은 기대값을 통과한다 — **통과**, 아래 검증 절.
4. **다섯 화면 대조와 기록 (완료).** 초기 화면·로드 후 화면, 그리고 **시나리오의 단계마다** 다섯 판독이 deep-equal인지 단언하고 불일치를 단계 단위로 보고한다. 콘솔·페이지 예외 수집이 붙어 있다. **기준 테스트:** M2-11 시나리오가 다섯 종에서 일치하고 콘솔 오류가 0이다 — **통과.**
5. **검증력 확인(주입) (완료).** 커넥터 한 종에 결함 2종을 주입해 **그 종만** 실패하는 것을 확인했고, 기대값이 이름 붙이지 않은 필드를 한 데모에서만 바꿔 **일치 단언만** 걸리는 것도 확인했다. **기준 테스트:** 주입 전부가 잡히고 `diff`로 복원이 확인된다 — **통과**, 아래 검증 절.
6. **남은 항목 이식 (진행 중).** 체크리스트 항목을 시나리오로 옮긴다. 이미 React로 통과한 것을 먼저 옮겨 **다섯 종으로 넓히고**(회귀 감시가 생긴다), 그다음 미수행 12개를 항목 순서대로 채운다. **기준 테스트:** 항목마다 다섯 종 일치 + 기대값 통과, 그리고 체크리스트 칸에 DC8-8-08의 출처가 적혀 있을 것. **진행:** M2-11 항목 1·2·6(신규 통과), M2-10(이식 — 넷째는 `M2-11-6`이 겸함), M2-07·M2-05·M2-08·M2-09(이식). 거기에 **M2-12·13·14·15는 처음 수행해 통과했고, M2-16은 항목 1·3, M2-11은 항목 4가 통과했다** — 미수행 13 → **7개**. 시나리오 **34개**, `examples/shared` **86개**, 브라우저 스위트 **46개**, 조작 **51개**. **다섯 종 증거가 붙은 항목: M2-05·07·08·09·10·11·12·13·14·15.**
7. **관측 카드 (신규).** `inspectCache()`·`inspectMutations()`를 화면에 올리고, 소유자 수와 환경 listener 수를 행으로 둔다. 조작 `관측 구독 해제`·`관측 구독 재개`를 더한다. **기준 테스트:** 다섯 데모에서 캐시 표의 소유자 수가 `프로필 2 / readonly 1`로 읽히고, `key를 live/b로 전환` 뒤 `live/a`가 owners 0이 되며, 구독 해제 뒤 이벤트 수가 `0`에 머문다.
8. **둘째 client (신규).** 같은 환경·같은 key에 둘째 `SyncClient`를 열고 조작으로 해제한다. **기준 테스트:** 두 캐시 표가 같은 `profile` 줄을 따로 들고, 한쪽의 편집이 다른 쪽에 보이지 않으며, probe를 해제하면 `환경 listener 수`가 2 → 1로 돌아온다.
9. **여러 명령의 순서 (신규).** scope를 선언한 독립 명령과 선언하지 않은 명령을 나란히 두고, 연결 저장의 장벽까지 한 자리에서 읽는다. **기준 테스트:** 같은 scope의 둘째 명령이 `queued`로 남고 **WRITE가 1건뿐**이며, 앞선 작업을 완료하면 둘째가 `pending`으로 올라갈 것.
10. **번들 페이지 러너 (신규).** `examples/bundles`의 8개 페이지를 실제 Chromium에서 열어 그 페이지들이 이미 인쇄하는 `판정` 행을 읽는다. **기준 테스트:** ESM 네 조합과 UMD 네 로드 순서가 모두 자기 판정에 도달하고, 콘솔 오류가 0일 것.
11. **Test Hardening과 통합.** 시나리오가 실제로 판정하는지 항목별로 주입 1종씩 확인한다. SSR 데모(React 5191·Vue 5192)의 hydration과 `examples/bundles`의 UMD script 태그 로드를 시나리오로 넣는다. **기준 테스트:** hydration 경고가 콘솔 수집으로 잡히고, UMD 네 조합의 판정 행을 실제 브라우저에서 읽는다.

- 다섯 데모가 같은 시나리오 집합을 실제 브라우저에서 통과하고, 판독이 서로 일치한다.
- 커넥터 결함 주입이 그 데모에서만 실패한다(DC8-8-07).
- 체크리스트의 모든 e2e 칸에 출처가 적혀 있다(DC8-8-08).
- 사람이 볼 항목이 이름으로 남아 있고, 그중 표본이 수행돼 있다(DC8-8-09).
- `pnpm test:e2e`가 문서화된 명령 하나로 재현된다. 19단계 gate 결과는 불변이다.

## 위험과 주의

- **장치가 초록인 것이 화면이 옳다는 뜻은 아니다.** 19단계 gate가 매번 통과하는 동안 손으로 데모 결함 열넷(B8-7-01~14)이 나왔다. 자동화가 놓친 이유는 자동이라서가 아니라 화면을 보지 않았기 때문이고, 이 장치는 그 하나를 고치는 것일 뿐이다. 기대값이 틀리면 다섯 종이 다정하게 같이 틀린다 — **다섯 일치는 커넥터 증거이고 정확성 증거가 아니다.**
- **시나리오는 클릭 수열이 아니라 판정이다.** "버튼을 눌렀다"만 기록하면 [B8-7-05](./MANUAL_TEST_CHECKLIST.md#b8-7-05)(라벨이 동작과 달랐다)를 그대로 재현한다. 단계마다 무엇이 참이어야 하는지를 기대 판독으로 적는다.
- **정지 조건을 화면이 갱신하는 값으로 잡는다.** [B8-7-13](./MANUAL_TEST_CHECKLIST.md#b8-7-13)이 그 함정이었다. 재시도 한 번은 완료 두 번이고, 시나리오는 횟수를 세지 말고 조건이 만족될 때까지 돈다.
- 브라우저 내려받기(~수백 MB)와 예제 빌드가 선행 조건이다. CI에 넣을지는 이 단계의 결정이 아니다.
- Playwright의 `webServer` 다섯은 포트 충돌에 약하다. 데모의 dev 포트(5181~5186·5191·5192)와 겹치지 않는 대역을 쓴다.
- 판독기가 `toLocaleTimeString()` 같은 지역·시각 의존 값을 읽으면 기록이 매 실행 달라진다. 시간 열은 판독에서 제외하거나 존재 여부만 본다.

## 검증

### 단계 1 — 첫 실제 브라우저 실행 (2026-09-26)

`pnpm test:e2e`가 예제 5종을 빌드하고, 각자의 `dist`를 4181~4185에서 `vite preview`로 띄우고, Chromium(headless shell 153.0.8010.12)에서 다섯 페이지를 열어 조작 버튼 집합을 카탈로그와 대조한다. **5/5 통과, 콘솔 오류 0.** 이것이 **Preact·Vue·Svelte·Solid의 첫 브라우저 증거**다 — 이 문서 전까지 브라우저에서 확인된 데모는 React 한 종뿐이었다.

**검증력 확인 — 데모 한 종에만 결함을 주입해 그 종만 실패했다.** Solid 데모의 버튼 루프를 `group.operations.filter(([id]) => id !== 'refetch')`로 바꿔 버튼 하나를 빼자:

| 검사 | 결과 |
| --- | --- |
| `node scripts/check-example-operations.mjs` | **놓쳤다** — "다섯 데모가 모두 45개를 렌더한다"고 답했다 |
| `pnpm test:e2e` | **solid만 실패**, 나머지 넷 통과 |

소스 검사의 좁힘 탐지 정규식은 `OPERATION_GROUPS.filter|slice|find`를 보는데 주입은 `group.operations` 쪽이었다. **소스에 카탈로그를 렌더하는 코드가 있다는 것과 버튼이 화면에 났다는 것은 다른 명제이고**, 그 차이를 처음으로 실제로 잡았다. [DC8-5-01](./PHASE8_5.md)이 전제한 "화면이 갈리면 커넥터 탓"이 이제 탐지 가능하다. 주입 뒤 `diff`로 복원을 확인했다.

`pnpm gate` 19단계와 `pnpm check:examples`는 불변으로 통과한다 — `examples/e2e`의 스크립트 이름은 `test`가 아니라 `e2e`이므로 `pnpm -r test`(gate의 test 단계)가 브라우저를 열지 않는다. 새 워크스페이스는 `types:examples`의 타입 검사에는 포함된다.

### 단계 2 — 값 쪽 계약 (2026-09-26)

라벨과 카드 제목이 다섯 데모에 **각자 리터럴로 중복**돼 있었다. 실측해 보니 28개 라벨이 다섯 곳에서 정확히 일치했지만, 그것을 지키는 장치는 없었다. `examples/shared/src/fields.ts`가 `CARD_TITLE`·`FIELD_LABEL`·`CARD_FIELDS`를 갖고, 데모는 `label(field)`를 렌더하며 행에 `data-field`를 붙인다. 리터럴 라벨은 다섯 데모 전부에서 0개가 되었다.

같은 라벨이 resource 패널과 draft에 모두 나오므로(`도시`·`우편번호`·`version / conflicts`) 판독 범위는 페이지가 아니라 **카드**다 — `[data-card="resource-a"] [data-field="status"]`. `draftDirty`만 별도 id인데, 화면이 resource에는 `dirty (로컬 차이)`, draft에는 `dirty`라고 적기 때문이다. 표를 깔끔하게 만들자고 사람이 읽는 글자를 바꾸지는 않는다.

Vue·Svelte는 인라인 `div.row`를 쓰고 있어 `Row`/`Flag` 컴포넌트를 새로 만들었다(React·Preact·Solid에는 이미 있었다). 값이 편집 가능한 `도시` 행은 기본 슬롯을 바꿔 끼운다. 카드별 필수 field는 `always`와 `onceLoaded`로 갈라 둔다 — 로드 전에 값 행을 요구하는 검사는 데모에게 **없는 기준을 보여 달라고** 요구하는 것이고, 그것이 M2-04가 금지하는 바로 그 화면이다.

**이번에도 한 종만 실패했고, 이번 것은 주입이 아니라 실제 누락이었다.** Solid의 `Row`·`Flag`에 `data-field`를 붙이는 것을 빠뜨렸는데, 다른 넷이 통과하는 동안 solid만 실패했다. 타입 검사도 빌드도 소스 검사도 통과한 상태였다 — 속성이 없어도 컴파일에는 아무 문제가 없다. 이어서 Vue의 `data-card="requests"`를 지우는 주입 1종으로 카드 범위도 확인했고, vue만 실패했다. 복원은 `diff`로 대조했다.

| 확인 | 결과 |
| --- | --- |
| 다섯 데모 × 계약 2종 | **10/10 통과**, 콘솔 오류 0 |
| Solid의 `data-field` 누락(실제) | solid만 실패 |
| Vue의 `data-card` 제거(주입) | vue만 실패 |
| `pnpm gate` 19단계 / `check:examples` | 불변 통과(다섯 데모 45개 렌더) |

### 단계 3~4 — DOM 판독기와 다섯 화면 대조 (2026-09-26)

`read.ts`의 `readScreen(page)`가 카드별 `data-field` 행과 요청 표의 안정적인 세 칸을 읽어 `ScreenReading`을 만든다. 모델도 `window` 전역도 읽지 않는다(DC8-8-01). 없는 카드는 빈 값이 아니라 **없는 것으로** 둔다 — draft 카드는 분기 전에는 존재하지 않고, 그것을 빈 카드로 읽으면 데모 간 차이가 묻힌다. 계약에 없는 field가 화면에 있으면 던진다.

그 판독기로 **초기 화면의 다섯 데모가 완전히 일치하는 것을 확인했다** — 31개 행과 요청 표 전체가 문자 단위로 같다. 이 프로젝트에서 DC8-5-01의 전제가 단언된 것은 이번이 처음이다. 부수 효과로, 라벨을 공유 표로 옮긴 이번 리팩터가 **화면 글자를 바꾸지 않았다**는 것도 같은 판독으로 확인됐다.

**검증력:** Svelte의 `고정한 제출` 자리 표시자만 `(없음)` → `(none)`으로 바꾸자 대조 테스트가 `svelte differs from react`와 함께 그 한 칸을 지목하며 실패했다. 복원은 `diff`로 대조했다.

**일치는 정확성이 아니다.** 다섯이 같이 틀릴 수 있고, 그것을 잡는 것은 시나리오의 기대값이다(DC8-8-03). 이 테스트가 좁히는 것은 "어디서 갈렸는가"이지 "무엇이 옳은가"가 아니다.

### 단계 3~4 (이어서) — 첫 대조가 찾은 결함 둘 (2026-09-26)

로드 **후** 화면까지 대조 범위를 넓히자 곧바로 둘이 나왔다. 값 행은 기준이 있어야 존재하므로 초기 화면 대조로는 닿을 수 없는 자리였다.

**[B8-7-15](./MANUAL_TEST_CHECKLIST.md#b8-7-15) — 같은 객체가 세 가지로 그려졌다.** `사무실` 값은 객체이고, 템플릿의 기본 문자열화는 프레임워크마다 다르다 — React·Preact·Solid `JSON.stringify`, Vue 들여쓴 JSON, **Svelte `String()` → `[object Object]`**. Svelte 화면은 그 값을 보여주지 못했고 그 행은 M2-15가 읽어야 하는 행이다. 다섯 데모가 모두 타입 검사·빌드·소스 검사를 통과하고 각자 잘 렌더하고 있었다. 문자열화를 공유 계약의 `show()`로 옮겼다 — **다섯이 같은 글자를 그려야 비교가 성립한다**는 것이 이 계약의 존재 이유다.

**CI-29 (라이브러리) — Vue 커넥터가 한 턴의 두 번째 쓰기를 버렸다.** `작업과 정책` 카드가 Vue에서만 항상 **이전 조작**을 보여줬다. 데모의 `bump()`는 tick·조작명·결과 셋을 한 턴에 쓰는데, `connectVue`의 에코 방지 가드가 **인바운드 갱신에서** 올라가고 microtask에서야 풀려 두 번째 이후 쓰기가 막혔다. 추적 기록:

| 누른 조작 | react·preact·svelte·solid | vue |
| --- | --- | --- |
| (시작) | `(없음)` | `(없음)` |
| `load` | `load` | `(없음)` |
| `가능한 요청 모두 완료` | `settle-all` | `load` |
| `focus 사건` | `focus` | `settle-all` |

**심어 넣은 커넥터 결함은 두 번 모두 커넥터 스위트가 먼저 잡았다.** 그것은 이 장치의 실패가 아니라 스위트에 대한 좋은 소식이다 — 그리고 [CI-29](../core-improvement/REQUIREMENTS.md)가 왜 스위트를 통과했는지도 정확히 말해 준다. | 실패 모양 | 어디를 보아야 하는가 |
| --- | --- |
| 한 종만 기대값 실패 | 그 커넥터 |
| 다섯이 함께 기대값 실패, 일치 유지 | fixture 또는 라이브러리 (또는 기대값이 틀렸다) |
| 기대값은 전부 통과, 일치만 실패 | 어떤 기대값도 보지 않는 자리의 화면 차이 |

주입 3종 모두 원본과 `diff`로 대조해 복원했다.

### 단계 6 — M2-14가 찾은 것 (2026-09-27)

`draft.apply()`는 레코드 전체를 한 번에 쓴다(`packages/state-ref/src/draft/index.ts:398`). 그래서 원본의 변경이 `city` 한 줄이 아니라 **`(root)` 한 줄**로 기록된다 — 라이브러리의 원자적 쓰기 성질이고 결함이 아니다. 문제는 그 다음이었다.

**[B8-7-19](./MANUAL_TEST_CHECKLIST.md#b8-7-19) — 적용한 변경을 영원히 제출할 수 없었다.** 데모의 `제출할 변경 고정`이 `change.path[0]`으로 DTO 경로를 거르는데 루트 변경에는 `path[0]`이 없다. 고정이 **변경 0건**을 골라 저장이 아무것도 보내지 않았고, 원본은 **보낼 수 없는 변경을 안은 채 영구히 dirty**였다. 이 항목의 넷째 문장("별도 mutation 성공·기준 수용 후 resource 변경이 해소된다")이 성립하지 않는 상태였다.

**라이브러리가 아니라 데모의 가정이 틀렸다** — 모든 변경에 leaf 경로가 있다고 본 것이다. 루트 변경은 레코드 전체를 담으므로 DTO가 싣는 경로가 그 안에 있고 제출 가능하다. 고침 뒤 고정이 1건을 고르고, 저장 성공 뒤 원본이 clean이 된다.

**이 결함은 다섯 종이 함께 틀린 부류다** — 공유 모델의 문제이므로 화면 대조로는 절대 나오지 않는다. 나온 이유는 **기대값이 체크리스트 문장을 그대로 적었기** 때문이다. 5단계의 표에서 "다섯이 함께 기대값 실패"에 해당하고, 이번에는 주입이 아니라 실제였다. **일치 단언만으로는 부족하다는 증거이기도 하다.**

### 단계 7 계획 — 관측 카드가 여는 것과 열지 않는 것 (2026-09-27)

먼저 모델에 일회용 probe를 걸어 **카드에 무엇이 실제로 나오는지 측정**했다(그 습관이 매번 값을 줬다: 기대값은 측정한 문자열에서 쓴다). 측정으로 확인한 것:

| 시점 | `inspectCache()` |
| --- | --- |
| 조작 전 | `profile owners=2 pending/idle`, `profile/readonly owners=1 pending/idle`, `size()=2` |
| `최초 조회` 뒤 | 둘 다 `pending/fetching` |
| 완료 뒤 | 둘 다 `success/idle loaded=true` |
| `key live/a로 활성화` | `live/a owners=1` 추가, `size()=3` |

| `표시 비활성화`·`표시 해제` | `live/a`·`live/b` 모두 owners 0, **`size()`는 4 그대로** |
| `저장 실행` 진행 중 | `inspectMutations()` = `#1 pending scope=null attempt=0 idem=false linked=[profile]` |

**owners 2가 화면에 처음 나온다.** 두 패널이 한 key를 공유한다는 것은 [DC8-5-01](./PHASE8_5.md)의 전제이자 M2-03의 내용인데, 지금까지 화면에는 그 사실을 말하는 숫자가 없었다 — 두 카드가 같은 값을 보여 주는 것으로 **추론**하고 있었다.

이 카드가 닿는 것:

- **M2-19 7항** — 조회 상태·소유자 수·생성/제거가 `inspectCache()`에서 맞고, 이벤트에 payload가 없고, 구독 해제 뒤 이벤트가 오지 않는다. 네 문장 전부.
- **M2-19 13항** — 미종료 WRITE만 보이고, 실행은 `pending`, 종료 작업은 목록에서 빠지고, 이벤트에 입력 DTO·응답·오류·idempotency 키 값이 없고, 구독 해제 뒤 이벤트가 없다. **`queued`만 남는다** — scope 대기를 만들려면 둘째 mutation이 필요하다.
- **M2-11 5항의 남은 절반** — `표시 비활성화`·`표시 해제` 뒤 **구독이 남지 않는다**를 owners 0으로 확인한다(DC8-8-15). 첫 문장("같은 key를 보는 둘째 view의 공유 READ")은 여전히 둘째 view를 요구한다.
- **M2-18 4항의 첫 문장** — "시작 전 query는 환경 listener를 만들지 않는다". 관찰자는 `load()`/`refetch()`에서만 `start()`하므로(`packages/sync/src/index.ts:1070`) 갓 열린 화면의 listener 수는 **0**이고, 그것이 화면에서 읽힌다.

이 카드가 **열지 않는 것**, 그리고 왜:

- **polling timer 수.** 데모는 `refetchInterval: false`라 timer가 애초에 생기지 않는다([DC8-5-12](./PHASE8_5.md) — fixture는 sync의 시계를 제어하지 못한다). 항상 0인 행은 아무것도 증명하지 않으므로 두지 않는다.
- **"dispose 뒤 listener가 남지 않는다"** (M2-18 4항의 뒷문장). 마지막 시작 관찰자를 해제해야 하는데 패널 조회의 수명은 화면의 수명과 같다. **둘째 client**를 같은 환경에 열고 그것만 해제하면 닿는다 — 그리고 그것은 M2-19 7·13항이 말하는 "**client별**"을 판정하는 유일한 길이기도 하다. 다음 단계 후보.
- **draft 구독의 누적** (M2-18 1항). 캐시 항목 수·소유자 수·이벤트 수의 평탄함은 client가 보는 누적이 0이라는 뜻이고, draft가 원본에 남긴 구독 수는 공개 표면에 없다. 셀 수는 있다 — 살아 있는 draft 수만큼만 알림이 오는지 세는 것 — 그러나 그것은 별도 계측이다.


**M2-19는 이 장치의 범위를 넘는다.** 15항목이 요구하는 것은 대체로 새 데모 화면이며, 그 대부분은 `packages/sync`의 자동 테스트가 이미 고정하고 있다. 브라우저에서 무엇을 다시 확인할 값이 있는지를 항목별로 먼저 골라야 한다 — 전부 옮기는 것은 목표가 아니다.

### 단계 6 — `liveView` 카드, 그리고 내가 만든 비반응형 행 (2026-09-27)

데모에 `liveView` 카드를 만들어 M2-11 넷째 항목에 닿았다. 라이브러리에는 Phase 5부터 있던 기능이고 데모에만 없었다. 두 key가 **서로 다른 값**을 답하도록 mock을 거쳐 태깅한 것이 핵심이다 — 같은 값이면 "이전 key의 늦은 결과가 새 표시에 들어가지 않았다"가 보이지 않는다([DC8-5-48](./PHASE8_5.md)과 같은 함정).

**그리고 장치가 내 실수를 잡았다.** 카드에 `조회 핸들` 행을 두고 `model.liveView.query`를 읽었는데 그것은 **반응형이 아니다.** React·Preact는 전체를 다시 그리므로 우연히 맞았고, **Svelte·Solid만 낡은 값을 보여 줬다** — `liveHandle: expected 있음, got (없음)`. [B8-7-13](./MANUAL_TEST_CHECKLIST.md#b8-7-13)과 정확히 같은 부류가, 이번에는 **방금 내가 쓴 행**에서 나왔다.

그 행의 값은 `queryKey !== null`과 동일하므로 **행을 없앴다** — 반응형으로 바꿔 같은 사실을 두 번 보여 주는 대신에. 교훈은 카드에 올리는 값은 반응형 출처에서 와야 한다는 것이고, 이 프로젝트에서 세 번째로 같은 실수다(B8-7-13, 그리고 Preact의 draft 상태 B8-7-18).

### 단계 7 — 관측 카드, 그리고 장치가 잡은 내 실수 (2026-09-27)

`inspectCache()`·`inspectMutations()`와 소유자 수·환경 listener 수를 화면에 올렸다. 조작 **51 → 54개**(`관측 구독 해제`·`관측 구독 재개`·`live/a 캐시 항목 제거 시도`), 시나리오 **34 → 39개**, `examples/shared` **86 → 91개**, 브라우저 스위트 **46 → 51개**. `pnpm test:e2e` **51/51 통과**, 콘솔 오류 0, 19단계 gate 불변.

**owners 2가 화면에 처음 나왔다.** 두 패널이 한 key를 공유한다는 것은 [DC8-5-01](./PHASE8_5.md)의 전제이고 M2-03의 내용인데, 그것을 말하는 숫자가 화면에 없어 **두 카드가 같은 값을 보이는 것으로 추론**해 왔다. 이제 `profile owners=2`가 한 줄로 서 있다.

**장치가 내 실수를 또 잡았다 — 이번에는 다른 모양으로.** 처음에는 관측 구독 하나가 카드를 다시 그리는 일까지 겸하게 했다. 그래서 `관측 구독 해제`를 누르면 캐시 표가 그 자리에서 얼어붙었고, 러너가 **다섯 데모 전부에서** 같은 칸을 지적했다:

```
react  step 7: cache[0]/status: expected success / idle, got success / fetching
preact step 7: (같음)   vue step 7: (같음)   svelte step 7: (같음)   solid step 7: (같음)
```

다섯이 함께 실패하는 모양은 **커넥터가 아니라 fixture나 기대값**을 가리킨다([단계 5](#단계-5--주입으로-확인한-두-가지-2026-09-26)의 표). 이번에는 fixture였고, 원인은 **화면을 다시 그리는 일을 시험 대상인 핸들에 맡긴 것**이다 — [B8-7-13](./MANUAL_TEST_CHECKLIST.md#b8-7-13) 계열의 네 번째 사례이되, "출처가 비반응형"이 아니라 "**갱신 경로가 조작으로 끌 수 있는 것**"이라는 새 변종이다. 두 쌍으로 갈라 고쳤고([DC8-8-17](#요구와-결정)), 그 결과 판정이 **더 강해졌다**: 같은 흐름에 살아 있는 listener가 표를 갱신하는 동안 해제한 listener만 0을 세므로, `0`이 "이벤트가 흐르지 않았다"가 아니라 **"해제가 listener 단위로 성립했다"**를 말한다.

**주입 2종으로 판정력을 확인했다**(DC8-8-07).

| 주입 | 결과 |
| --- | --- |
| `releaseInspection`이 핸들을 놓지 않고 플래그만 뒤집게 함 (fixture) | **다섯 전부 실패**, `observedEvents: expected 0 / 0, got 4 / 0` — 새는 곳을 행 이름으로 지목 |
| Solid만 캐시 표의 마지막 줄을 버리게 함 (`cache.slice(0, -1)`) | **solid만 실패**, `cache: expected 4 row(s), got 3 (profile, profile/readonly, live/a)` — 데모·단계·빠진 줄을 모두 말함 |

둘 다 scratchpad에 원본을 두고 복원 뒤 `diff`로 동일함을 확인했다.

**같은 버튼이 두 번 다르게 답한다.** `client.remove()`는 소유자·dirty·미확정·진행 중 중 하나라도 있으면 거절한다(`packages/sync/src/index.ts:1588`). 그래서 `live/a 캐시 항목 제거 시도`는 표시가 그 key를 보고 있을 때 **거절**되고, `표시 비활성화` 뒤에는 **제거**된다(`cacheSize` 3 → 2). M2-19 7항의 "생성/제거"에서 제거 쪽이 그것으로 닿았다.

**닿지 못한 것과 왜:**

- **`queued` phase** — scope 대기를 만들려면 둘째 mutation이 필요하다. M2-19 13항의 한 문장이 그것만 남았다.
- **"client별"** — M2-19 7·13항의 첫 단어다. 판정하려면 둘째 client가 필요하고, 그것은 M2-18 4항의 "dispose 뒤 listener가 남지 않는다"와 **같은 계측**이다(패널 조회의 수명은 화면의 수명과 같아 해제할 수 없다). 다음 단계로 가장 값이 높은 것이 이것으로 바뀌었다.
- **polling timer** — 데모는 `refetchInterval: false`라 timer가 생기지 않는다. 항상 0인 행은 증거가 아니므로 두지 않았다(설계 절에 기록).

### 단계 8 — 둘째 client, 그리고 격리가 화면에 선 자리 (2026-09-27)

같은 환경·같은 key `profile`에 둘째 `SyncClient`를 열고 조작으로 해제한다. 조작 **54 → 58개**(`둘째 client 열기·조회·편집·해제`), 시나리오 **39 → 43개**, `examples/shared` **91 → 95개**, 브라우저 스위트 **51 → 55개**. `pnpm test:e2e` **55/55 통과**, 콘솔 오류 0, 19단계 gate 불변, `packages/` 무변경.

**측정으로 확인한 것** (probe로 먼저 재고 기대값은 그 문자열에서 썼다):

| 조작 | 주 client | 둘째 client | 환경 listener |
| --- | --- | --- | --- |
| `최초 조회` + 완료 | `profile owners=2 success/idle`, `profile/readonly owners=1` | (없음) | 1 |
| `둘째 client 열기` | 그대로 | `profile owners=1` **`pending / idle`** — 주 client가 이미 로드됐는데도 기준을 물려받지 않는다 | **1 그대로** |
| `둘째 client 조회` | 그대로 | `pending / fetching` | **2** |
| 완료 | 그대로 | `success / idle`, 도시 `서울` | 2 |
| `둘째 client에서 도시 → 제주` | 패널 둘 다 **`서울`·clean** | `제주`·dirty·version `1 / 0` | 2 |
| `도시 → 부산` | 패널 둘 다 `부산`·dirty·version `1 / 0` | **`제주`·version `1 / 0` 그대로** | 2 |
| `둘째 client 해제` | 그대로 | 모든 행 `(해제됨)`, 캐시 표 빈 목록 | **1** |

**요청이 따로 나간다.** 주 client가 `profile`을 이미 들고 있는데도 `둘째 client 조회`가 READ를 2 → 3으로 늘리고 그 key는 `profile`이다. **캐시가 다르면 공유할 진행 READ가 없다** — [M2-03](./MANUAL_TEST_CHECKLIST.md#m2-03) 여섯째 항목(R2-07)이 화면에서 성립하는 방식이다.

**그리고 첫째 항목이 반대 방향으로 성립한다.** 한 client 안에서 패널 두 장은 `owners=2`로 한 항목을 공유하고, `최초 조회`는 패널 조회 하나만 낸다 — **패널 B는 아무것도 요청하지 않았는데 함께 `pending / fetching`이다.** 그것이 "진행 READ는 공유한다"이고, 앞 단계가 만든 소유자 수 덕에 화면에서 말할 수 있게 됐다.

**두 이벤트 계수기가 따로 센다.** 주 client에서 `저장 실행` → 완료까지 지나가는 동안 그 카드의 수는 오르고 둘째 client의 수는 자기 client에서 일어난 일(자기 READ 3건)에 머문다. `inspectCache()`·`subscribeCache()`·`inspectMutations()`가 **client별**이라는 것이 두 카드를 나란히 두어 읽힌다.

**주입 2종으로 판정력을 확인했다**(DC8-8-07).

| 주입 | 결과 |
| --- | --- |
| `openProbe`가 새 client를 만들지 않고 주 client를 그대로 씀 | **다섯 전부 실패**, 세 시나리오 모두. 메시지가 무엇이 깨졌는지 그대로 말한다: `probe/status: expected pending / idle, got success / idle`(기준을 물려받았다), `probe cache: expected 1 row(s), got 2`(표가 합쳐졌다), 그리고 결정적으로 **`resource-a/city: expected 서울, got 제주`**(편집이 패널로 새어 나갔다) |
| Vue의 probe 카드만 주 client의 소유자 수를 인쇄(복사 실수 모양) | **vue만 실패**, `probe/cacheOwners: expected 1, got 3` — 데모·단계·행을 모두 말함 |

둘 다 scratchpad에 원본을 두고 복원 뒤 `diff`로 동일함을 확인했다.

**구조 변경 하나.** 캐시·WRITE 표의 판독을 **카드 범위**로 바꿨다([DC8-8-20](#요구와-결정)) — 두 client의 항목을 한 목록에 섞으면 `client별`이 흐려지기 때문이다. 그리고 **빈 표도 판독**이므로(관측 카드의 `미종료 WRITE 없음`) 표 소유를 계약에 선언했다(`CACHE_TABLE_CARDS`·`MUTATION_TABLE_CARDS`): 줄이 있는지로 추론하면 "줄이 없다"와 "표가 없다"를 구별할 수 없고 두 판독기가 이유 없이 갈린다. `keyText`는 계약 모듈로 옮겼다 — 모델이 투영을 import하게 되면서 순환이 될 자리였다.

**닿지 못한 것:** M2-03의 셋째·넷째·다섯째 항목이다. fresh/stale/GC는 `staleTime 0`과 벽시계 `gcTime`에 묶여 있고([DC8-5-12](./PHASE8_5.md)), `refetchOnFocus`의 `true`/`'always'`/`false` 구분은 정책이 다른 조회 세 개를, polling은 `refetchInterval`을 요구한다.

### 단계 9 — 여러 명령의 순서, 그리고 `queued`가 이름표가 아니라는 것 (2026-09-27)

조작 **58 → 60개**(`독립 명령 실행 (순서 지정 없음)`·`(scope 지정, 순서 보장)`), 시나리오 **43 → 46개**, `examples/shared` **95 → 98개**, 브라우저 스위트 **55 → 58개**. `pnpm test:e2e` **58/58 통과**, 콘솔 오류 0, 19단계 gate 불변, `packages/` 무변경.

**연결하지 않은 명령을 쓴 것이 설계의 핵심이다.** 연결 저장은 같은 조회에 다른 연결 저장이 떠 있으면 **거절된다** — 그래서 연결 저장 두 개로는 순서를 시험할 수 없다. 순서가 시험 가능한 유일한 모양은 겹칠 수 있는 명령이고, 그것이 R2-08의 `resource 없는 명령`이다. 그리고 그 거절 자체가 M2-11 셋째 항목의 **충돌 정책** 쪽 답이므로, 세 시나리오가 한 항목의 두 문장을 나눠 맡는다.

| 시나리오 | 읽히는 것 |
| --- | --- |
| `M2-11-3-unordered` | scope 없는 명령 둘이 **모두 `pending`**, WRITE `2`건, 진행 중 `2` — sync는 선언하지 않은 순서를 만들지 않는다 |
| `M2-11-3-scoped` | 같은 scope면 `#1 pending` · `#2 queued`, 그런데 **WRITE는 1건뿐이다**. 완료하면 `#1`이 목록에서 빠지고 `#2`가 `pending`으로 올라가 WRITE가 2건이 된다 |
| `M2-11-3-barrier` | 연결 저장 둘째는 시작되지 않는다. 줄 하나, WRITE 1건, 화면이 이유를 말한다 |

**`queued`는 이름표가 아니다.** 이 단계에서 가장 값 있는 판독은 `phase` 열이 아니라 **요청 수**다: 같은 scope의 둘째 명령이 `queued`인 동안 서버에 나간 WRITE는 **1건**이다. `phase`만 봤다면 "라벨이 그렇게 붙었다"까지만 말할 수 있었고, 요청 표가 함께 있어 **요청이 아직 떠나지도 않았다**가 말해진다. 두 계측이 한 화면에 있어야 생기는 판정이다.

**주입 2종으로 판정력을 확인했다**(DC8-8-07).

| 주입 | 결과 |
| --- | --- |
| `scope` 인자를 떨어뜨림 (모델) | **다섯 전부 실패**, 네 줄이 함께 말한다: `mutations[1]/phase: expected queued, got pending`, `mutations[0]/scope: expected address, got (없음)`, 그리고 **`requests/counts: expected 2 / 1, got 2 / 2`** — 순서가 사라지자 요청이 둘 다 나갔다 |
| Preact의 WRITE 표만 `phase`를 `pending`으로 고정 | **preact만 실패**, `mutations[1]/phase: expected queued, got pending`. 무심히 보면 맞아 보이는 화면이고 **`queued` 줄 하나만 어긋난다** |

둘 다 scratchpad에 원본을 두고 복원 뒤 `diff`로 동일함을 확인했다.

**M2-19 13항이 이것으로 통과가 됐다.** `queued`가 그 항목의 마지막 미수행 문장이었다.

| --- | --- |

**`CI-24`가 같은 되살아남을 패스 *안*에서 이미 막아 놨다** — 그 주석이 이 부류를 정확히 묘사하고 있다("reading a path re-registered it … a resurrection nothing could undo"). 막은 것은 한 입구였고, 앱이 화면을 다시 그리며 읽는 입구는 열려 있었다. `CI-24` 기록의 "패스 밖 `abort()`는 정상(실측 A·D·E)"도 **abort 뒤에 읽는 경우를 지나갔다**.

**왜 338개 테스트가 통과하고 있었나.** `hardening.ts`의 "패스 밖에서 signal이 발화하면 해제된다"는 `abort()` 다음에 **곧바로 쓴다.** 사이에 읽지 않으니 재등록할 틈이 없다. 버튼마다 repaint하는 페이지는 예외 없이 그 사이에 읽고, **그 화면을 실제 브라우저에서 처음 연 것이 이 단계다.**
